# taskcomm

Spring Boot стартер, инкапсулирующий таск-менеджмент и коммуникации с внешними системами.
Подключив стартер, приложение-потребитель получает: создание задач и процессоров по типам задач,
персистентность, повторы при ошибках, разбиение задач на подзадачи (`TaskUnit`) и группы подзадач
(`TaskBatch`), REST API для управления задачами, а также аналогичный механизм для коммуникаций
(процессоры по источнику/назначению) с горизонтальным масштабированием.

> **Статус:** задачи, коммуникации, REST и наблюдаемость сделаны, впереди — публикация и первый
> релиз ([roadmap](docs/roadmap.md)). Этот файл и правила по темам в [docs/rules/](docs/rules/) —
> правила, а не описание кода. Если код с ними разошёлся, приоритет у правил: сначала обсуди
> расхождение, потом меняй правило или код.

### Каталог версий

Версии фиксируются явно, в version catalog внутри `settings.gradle`; Gradle — в
`gradle-wrapper.properties`.

**Не пиним** — версии приходят из BOM Spring Boot: Micrometer и его реестры, драйвер PostgreSQL,
Tomcat, Jackson 3, Liquibase (только в тестах). `jackson-dataformat-xml` — тоже из BOM и только `compileOnly`:
потребителю она не приезжает, SOAP-потребитель подключает её сам ([ADR 0135](docs/adr/0135-communication-engine.md)). Так же `spring-webmvc` и `spring-security-web`: REST включает потребитель, MVC и Security у него свои ([ADR 0140](docs/adr/0140-rest-controllers.md)). Так же `micrometer-core` и `spring-boot-health`: метрики и health indicator появляются только у того, у кого Micrometer и Actuator свои ([ADR 0141](docs/adr/0141-observability-instance.md)). Явный пин старой ветки Micrometer против Boot ломает Actuator, а пин драйвера
вниз нарушает наше же правило «не понижать версии зависимостей».

В каталоге нет и не должно быть Spring Cloud, json-schema-validator, logback-access и logstash:
в дизайне taskcomm они не участвуют, а каждая зависимость стартера приезжает всем потребителям.

### Граница между Spotless и Checkstyle

За форматирование отвечает **только Spotless**; Checkstyle — за то, чего форматтер не видит, и
**заваливает сборку**. Что из правил убрано и почему — в шапке `checkstyle.xml`; точечные исключения —
в `checkstyle-suppressions.xml` рядом с ним.

## Структура репозитория

```
taskcomm/
├── taskcomm-autoconfigure/        весь код: домен, реализация, REST, @AutoConfiguration
├── taskcomm-spring-boot-starter/  НИ ОДНОГО класса — только объявление зависимостей
└── taskcomm-bom/                  только версии: стартер и его необязательные зависимости
```

Внутри `taskcomm-autoconfigure`:

```
xyz.avasilev.taskcomm          TaskcommException и его общие наследники — публичный API,
│                              доступный всем пакетам без связи между подсистемами
├── execution/{api,internal}   агрегат Execution
├── task/                      подсистема задач
│   ├── api/                   модель и сервис; api/processor — контракты процессоров,
│   │                          api/inspection — чтение
│   └── internal/              корень — общая модель и SQL, дальше группы слоями
├── communication/             подсистема коммуникаций — так же, своей раскладкой
├── schema/internal/           проверка схемы, initialize, партиции и их граница — общее для
│                              подсистем, без api (ADR 0107)
├── rest/                      контроллеры и DTO (внутренняя реализация, не публичный Java API)
└── autoconfigure/             классы @AutoConfiguration и @ConfigurationProperties
```

**Публичный API — это всё, что лежит вне пакетов `internal`.** Изменение сигнатуры такого типа —
ломающее изменение, см. раздел «Совместимость».

**Внутри `internal` подсистемы — группы по обязанностям, выстроенные слоями**
([ADR 0143](docs/adr/0143-internal-subpackages.md)): группа зависит только от групп ниже себя.
Порядок слоёв — в `ArchitectureTest`, это и есть правило. Новый класс кладётся в группу своей
обязанности; `public` получает только то, что пересекает границу группы, внутри группы —
package-private. Тест лежит в подпакете своего предмета.

## Правила стартера

Это самый важный раздел: стартер подключают чужие приложения, и он не имеет права навязывать им
поведение.

- Автоконфигурации помечаются `@AutoConfiguration` и перечисляются в
  `taskcomm-autoconfigure/src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`.
  `spring.factories` для этого **не используется** — в Spring Boot 3 механизм удалён.
- Каждый бин объявляется явным `@Bean`-методом. Бин внутреннего типа — **без**
  `@ConditionalOnMissingBean`: заменить его можно было бы, только унаследовав класс из `internal`,
  и тогда внутренний тип стал бы API без обязательств совместимости
  ([ADR 0089](docs/adr/0089-no-storage-spi-explicit-extension-points.md)). Классы свойств — тоже
  без условия.
- **Бинов чужих типов, которые стартер потребляет сам, он не регистрирует** — ни `JsonMapper`,
  ни `TaskScheduler`, ни `Executor`, ни `ThreadFactory`, ни `TaskDecorator`
  ([ADR 0096](docs/adr/0096-no-foreign-type-beans.md)). Бин такого типа вытесняет автоконфигурацию
  Spring Boot или забирает `@Scheduled` / `@Async` потребителя. Маппер, планировщик и пулы —
  поля внутренних бинов, остановка — их забота.
- **Точки замены — бины потребителя с квалификатором стартера**, все необязательны; список
  ведётся явно — здесь и в [guide/evolution/compatibility.md](docs/guide/evolution/compatibility.md):
  `@TaskcommPayloadMapper` (`JsonMapper`), `@TaskcommScheduler` (`TaskScheduler`),
  `@TaskcommWorkerThreadFactory` (`ThreadFactory`), `@TaskcommWorkerTaskDecorator`
  (`TaskDecorator`). Отдельно — квалификаторы **выбора** `@TaskcommDataSource`
  и `@TaskcommTransactionManager` ([ADR 0094](docs/adr/0094-creation-always-in-transaction.md)):
  у них своего бина по умолчанию нет. Все квалификаторы — в `autoconfigure`.
- **Бинов чужих типов два, и стартер их отдаёт, а не потребляет**: `RequestMatcher` с именем
  `taskcommRequestMatcher` — только вместе с REST и при Spring Security на classpath; `HealthIndicator`
  с именем `taskcommHealthIndicator` — только при Actuator ([ADR 0141](docs/adr/0141-observability-instance.md)).
- Каждая подсистема выключается свойством `taskcomm.<подсистема>.enabled`, а **все сразу —
  `taskcomm.enabled`** ([ADR 0090](docs/adr/0090-root-switch-disables-everything.md)). Автоконфигурация
  подсистемы стоит под **составным условием** «корень и подсистема», оба по умолчанию `true`;
  условие — один класс в `autoconfigure`. Порядок `after` включённость не передаёт: без составного
  условия `taskcomm.enabled: false` выключил бы только корень, а поллеры, heartbeat, партиции
  и REST продолжили бы работать.
- **Никакого `@ComponentScan` в автоконфигурациях** и никаких `@Component` / `@Service` /
  `@Repository` на внутренних классах. Сканирование в стартере ломает потребителя непредсказуемым
  образом; все бины создаются вручную.
- **Не включать глобальные механизмы Spring за потребителя**: `@EnableScheduling`, `@EnableAsync`,
  `@EnableTransactionManagement` в автоконфигурациях запрещены — они меняют поведение всего
  приложения. Нужен планировщик — держи собственный полем внутреннего бина, бином его
  не регистрируй (см. выше).
- Порядок конфигураций задаётся через `@AutoConfiguration(after = ..., before = ...)`.
- Зависимости в `taskcomm-autoconfigure` объявляются как `compileOnly` / `optional`;
  реальные транзитивы собираются в `taskcomm-spring-boot-starter` через `api`.
- **Стартер не экспортирует BOM Spring Boot**, и ни один библиотечный модуль не публикует платформу
  ([ADR 0106](docs/adr/0106-starter-does-not-export-bom.md)): у Gradle-потребителя она подняла бы
  все зависимости из BOM до наших версий. Зависимости стартера — с явными версиями из каталога.
  Задача `verifyNoExportedPlatform` в составе `check` читает опубликованные `.module` и `.pom`
  и валит сборку, если платформа в них появилась.
- **Собственный BOM — `taskcomm-bom`**, его потребитель подключает сам
  ([ADR 0144](docs/adr/0144-taskcomm-bom.md)). Только ограничения версий, без зависимостей
  и без импорта чужих BOM: наши артефакты, прямые зависимости стартера и необязательные
  зависимости, которые включают функции. Список явный и закрытый — **новая необязательная
  зависимость стартера добавляется в BOM** вместе с решением, которое её вводит. Задача `verifyBom`
  валит сборку, если BOM тянет зависимости, импортирует чужой BOM или расходится со стартером.
- Подключён `spring-boot-configuration-processor` — свойства автодополняются в IDE потребителя.

### Регистрация обработчиков

Потребитель объявляет процессор — одного из трёх наследников `TaskProcessor`, либо
`CommunicationProcessor` — как обычный `@Bean` или `@Component` **в своём коде**. Стартер собирает
их инъекцией `List<TaskProcessor<?>>`. Не писать `ImportBeanDefinitionRegistrar` и не сканировать
classpath — Spring уже всё нашёл.

## Доменный словарь

| Тип                                                               | Что это                                                                                                                                                                            |
|-------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `Execution`                                                       | Набор связанных действий вокруг одного повода. Агрегат над задачами и коммуникациями                                                                                               |
| `Task`                                                            | Задача целиком: что нужно сделать над множеством бизнес-объектов потребителя                                                                                                       |
| `TaskBatch<TPayload>`                                             | Группа подзадач внутри задачи; `TPayload` — параметры группы                                                                                                                       |
| `TaskUnit<TPayload>`                                              | Подзадача: обработка **одного** бизнес-объекта. Минимальная единица работы и повтора                                                                                               |
| `TaskProcessor<TTaskPayload>`                                     | Запечатанный базовый контракт; потребитель реализует одного из трёх наследников                                                                                                    |
| `Communication<TRequest>`                                         | Коммуникация с внешней системой. **Атомарна**, на части не делится                                                                                                                 |
| `CommunicationProcessor<TRequest, TSyncResponse, TAsyncResponse>` | Запечатанный базовый контракт по транспорту; `TSyncResponse` — доменная форма синхронного ответа, `TAsyncResponse` — асинхронного (колбэка), `Void` у не ждущих. Пишет потребитель |

Ключевое ограничение модели: стартер **не знает и не должен знать**, какие бизнес-объекты
обрабатывает потребитель. Полезная нагрузка — параметр типа `TPayload`, непрозрачный для стартера.
Отсюда правило именования: доменные типы называют *единицу работы и её место в иерархии*, а не
содержимое. Имена вроде `Entity`, `Record`, `Document` запрещены — они утверждают что-то про
полезную нагрузку и вдобавок сталкиваются с `jakarta.persistence.Entity` и `java.lang.Record`.

Иерархия у задач и коммуникаций **намеренно разная**: `Task → TaskBatch → TaskUnit` против плоской
`Communication`. У коммуникаций нет батчей и единиц — одна коммуникация неделима, и повтор при
ошибке применяется к ней целиком. Не «унифицировать» две модели ради симметрии и не заводить
`CommunicationBatch` / `CommunicationUnit`.

Направление — **тип, а не значение поля**: `Communication` запечатан и разрешает только
`Inbound` (`source()`) и `Outbound` (`destination()`). Невалидную коммуникацию (обе стороны пустые, обе заполненные) нельзя собрать в принципе, а процессор
разбирает направление через pattern matching. В БД по-прежнему две колонки и признак направления.
Интерфейсы, а не записи, — как у `Task`: новое поле не ломает совместимость
([ADR 0134](docs/adr/0134-communication-public-api-shape.md)).

Нагрузка называется `requestPayload`, а не `payload`: доменных форм у коммуникации две — запроса
и ответа ([ADR 0055](docs/adr/0055-communication-exchange-storage.md)). У задач колонка остаётся
`payload`, и это расхождение подсистем сознательное.

Процессор ищется по внешней стороне — `source` для входящих, `destination` для исходящих.
Фактически **один процессор = один адаптер к одной внешней системе**: если в эту систему уходят
сообщения разных видов, разбирается с этим сам процессор.

**Задачи и коммуникации — две независимые реализации.** Захват, повторы и SQL у них похожи, но
общего кода между подсистемами нет и не должно быть. Дублирование здесь сознательное: подсистемы
обязаны меняться независимо. Не выносить `SKIP LOCKED`-захват, политику повторов и работу с арендой
в общий класс, даже если код выглядит одинаковым.

Расхождение уже перестало быть теоретическим: **у коммуникаций строка попытки создаётся вместе
с сущностью, а захват стал одноветочным** ([ADR 0054](docs/adr/0054-communication-attempt-lifecycle.md)).
Запросы захвата у подсистем разные по форме, и переносить форму одной на другую нельзя.

Так же запрещены имена, конфликтующие с ключевыми типами платформы и Spring: `TaskExecutor`
(есть `org.springframework.core.task.TaskExecutor`), `Package` (есть `java.lang.Package`,
и `package` — ключевое слово Java). По этому же правилу отвергнуто имя `Case` для агрегата —
`case` тоже ключевое слово ([ADR 0038](docs/adr/0038-execution-aggregate.md)).

## Стиль кода

- Конструкторная инъекция, поля `final`, `@RequiredArgsConstructor`. Полевая инъекция запрещена.
- Фичи Java 25 приветствуются: `record` для DTO и value-объектов, `sealed` для состояний,
  pattern matching в `switch`, text blocks для SQL.
- **Виртуальные потоки — с осторожностью и только по явному согласованию.** Pinning на
  `synchronized` в Java 25 больше нет (JEP 491), но он остаётся на нативных кадрах; главное же —
  узким местом становится пул JDBC-соединений, а не потоки.
- Маппинг — MapStruct, руками мапперы не писать.
- Логирование — `@Slf4j`, параметризованные сообщения (`log.debug("задача {} провалена", id)`),
  без конкатенации строк.
- `Optional` — только как возвращаемое значение; не поле, не параметр метода.
- Исключения наследуются от общего `TaskcommException` (корневой пакет); ошибки настроек и схемы
  при старте — `TaskcommConfigurationException`. Не глотать и не делать
  «залогировал и пробросил» одновременно.
- Javadoc обязателен для всех публичных типов и методов (то есть для всего вне `internal`).
- **Комментарии, Javadoc и сообщения коммитов — на русском языке.**
- **Кальки с английского запрещены.** Проверка простая: есть обычное русское слово — берём его;
  слово называет паттерн, технологию или ключевое слово — оставляем **латиницей**,
  не транслитерируем.
  - Уже спотыкались: **ретенция** → очистка, глубина хранения; **контенция** → конкуренция
    за строку; **гранулярность** → детализация.
  - Не трогать: **fan-in**, **fan-out**, **backoff**, **heartbeat**, `SKIP LOCKED` — это имена,
    а не кальки.
  - «Персистентность» — исключение: термин проекта с самого начала, менять его поздно и незачем.
- **Не изобретать терминов.** Либо обычное русское слово, либо термин, уже определённый
  в доменном словаре. Самодельное слово хуже кальки: оно выглядит устоявшимся, и читатель идёт
  искать определение, которого нет. Если подходящего варианта не нашлось и хочется завести
  новый термин — **спроси явно**, не вводи молча.
  - Уже спотыкались: **«миллионный путь»** про чтение, идущее по миллиону строк. Мало того что
    нигде не определено, так ещё и читается как порядковое числительное — «путь номер миллион».

Обязательства, которые проверяет Checkstyle, — пиши сразу так, а не переписывай после прогона:

- `this.` перед каждым обращением к полю (`RequireThis`).
- `final` на всех параметрах и локальных переменных (`FinalParameters`, `FinalLocalVariable`).
- `package-info.java` с Javadoc **в каждом `api`-пакете** (`JavadocPackage`; для `internal`
  и тестов подавлено в `checkstyle-suppressions.xml`). Отдельно `MissingJavadocPackage` требует
  Javadoc в любом заведённом `package-info.java`, где бы он ни лежал.
- Аббревиатуры в CamelCase: `SqlBuilder`, `JsonCodec`, `RestApiConfig` — не `SQLBuilder`
  и не `RestAPIConfig` (`AbbreviationAsWordInName`). Исключение — суффикс `IT` интеграционных тестов.
- Параметр типа — осмысленное имя с префиксом вида: `T` — тип, `E` — элемент коллекции,
  `K` и `V` — ключ и значение отображения: `TTaskPayload`, `TSyncResponse`, `EItem`. Однобуквенные
  имена запрещены ([ADR 0145](docs/adr/0145-meaningful-type-parameter-names.md)).
- Не более трёх `return` на метод, фигурные скобки обязательны даже для однострочников.
- `org.junit.jupiter.api.Assertions` запрещён импортом — только AssertJ.

## Тесты

- `*Test` — unit-тесты, `*IT` — интеграционные. Разделение — по имени класса: задача `test`
  запускает только `*Test`, задача `integrationTest` — только `*IT`, и она входит в `check`
  ([ADR 0108](docs/adr/0108-integration-test-task.md)). Класс с другим именем не запустит ни одна.
  Третье имя — `*LoadScenario`: нагрузочные сценарии, их запускает только задача `loadTest`,
  вне `check` ([ADR 0128](docs/adr/0128-claim-load-scenario.md)).
- **Интеграционные тесты — только на PostgreSQL в Testcontainers**
  ([ADR 0085](docs/adr/0085-tests-on-real-postgres.md)). H2 и другие встроенные базы не годятся:
  нет партиционирования с `ATTACH`, `jsonb`, `SKIP LOCKED` в семантике PostgreSQL, advisory-блокировок.
  Полный прогон требует Docker — локально и в CI; модульные тесты от него не зависят.
- Автоконфигурации проверяются через `ApplicationContextRunner`. Для каждой автоконфигурации —
  минимум три сценария: бины создаются по умолчанию; подсистема выключается своим
  `enabled=false`; подсистема выключается корневым `taskcomm.enabled=false`
  ([ADR 0090](docs/adr/0090-root-switch-disables-everything.md)). Плюс для **каждой точки замены
  из списка** — помеченный квалификатором бин потребителя берётся вместо нашего, а бин того же
  типа без квалификатора не берётся; и для каждой автоконфигурации — что бинов чужих типов она
  в контекст не добавляет ([ADR 0096](docs/adr/0096-no-foreign-type-beans.md)).
- ArchUnit-тест `ArchitectureTest` обязателен ([ADR 0087](docs/adr/0087-architecture-rules.md)); перечень
  границ пакетов — в нём. Единственное исключение — `execution.internal`, доступный внутренним
  пакетам обоих движков ([ADR 0114](docs/adr/0114-uuidv7-generator-in-execution-internal.md)):
  список его оснований закрыт, расширять молча нельзя. Новый пакет или подсистема — новые правила там же.
- Утверждения — AssertJ (`assertThat`), не `Assertions.assertEquals`.

## Совместимость и публикация

- Semver. Текущая версия — `2.0.0`.
- Мажорная версия поднимается **только** при потере обратной совместимости, и этого стараемся не
  допускать. Прежде чем менять публичную сигнатуру — предложи вариант с сохранением совместимости
  (перегрузка, `default`-метод, новый тип) и явно скажи, что альтернатива требует мажорной версии.
- Новое свойство конфигурации обязано иметь значение по умолчанию, сохраняющее прежнее поведение.
- Свойства и API не удаляются сразу: сначала `@Deprecated` с указанием замены, удаление — в
  следующей мажорной версии.

## Чего не делать без явной просьбы

- Не коммитить и не пушить. Изменения оставляй в рабочей копии, я коммичу сам.
- **Не коммитить напрямую в `main`** — даже когда коммит попросили явно. Сначала заводится
  отдельная ветка, коммит идёт в неё.
- Не понижать версии зависимостей.
- Не добавлять новые внешние зависимости в `taskcomm-autoconfigure` — каждая становится транзитивной
  для всех потребителей. Сначала предложи и обоснуй.
- Не менять публичные сигнатуры, не сказав об этом прямо.
- Не отключать и не подавлять правила Checkstyle / Spotless / Error Prone, чтобы «прошла сборка».
  Чини код, а не правило. Ложное срабатывание Error Prone на коде Lombok глушится точечно,
  не целым правилом.

## Порядок обсуждения

- **Ответ уточняющим вопросом на твой вопрос — это уточняющий вопрос, а не решение.** Услышав
  в ответ «а какую проблему мы решаем?» или «а какая цена такого-то варианта?», отвечай на
  заданное и **задавай свой вопрос повторно**. Выводить решение из формулировки встречного
  вопроса запрещено: вопрос выражает сомнение, а не выбор, и догадка о том, какой вариант за ним
  стоит, ошибётся ровно тогда, когда обсуждение важнее всего.
- Развилку закрывает человек. Пока прямого ответа нет, она открыта — сколько бы раундов
  ни потребовалось.

## Открытые вопросы

Не решено — если задача упирается в один из пунктов, спроси, не выбирай сам:

1. WebSocket-подписка на события задач — отложена. Главная нерешённая часть: как событие с одного
   инстанса доходит до UI, подключённого к другому. Кандидат — Postgres `LISTEN/NOTIFY`, потому что
   не требует новой инфраструктуры у потребителей; Redis отвергнут по этой же причине.
2. **Поиск по нагрузке коммуникаций.** Белый список полей объявлен только для задач —
   `searchableTaskFields()`, `searchableBatchFields()`, `searchableUnitFields()`
   ([ADR 0037](docs/adr/0037-search-field-registry.md)); у коммуникаций есть только лукап
   по `request_id`. Сценарий «найти коммуникации по параметру вне зависимости от исполнения,
   а потом посмотреть связанные задачи» этим не обслуживается и пока обходится фильтром
   по `source` / `destination` внутри дела
   ([ADR 0064](docs/adr/0064-entity-origin-links.md)).

   Что решать, когда дойдёт очередь: общий это реестр с задачами или свой; объявляет поля
   процессор коммуникаций или что-то ещё; и по какой из двух доменных форм идёт поиск —
   `request_payload`, `response_payload` или по обеим. Изменение аддитивное, а до первого
   релиза ещё и не ломающее, поэтому ждать его не обязано ни одно другое решение.
3. **Механизм событий после `process`.** Вопрос **спорный**, и пока это так, формулировка важнее
   вариантов: речь о мутации сущностей без аспектов — если такое понадобится. То есть о штатном
   способе для потребителя дотянуться до сущности по завершении обработки, вместо того чтобы
   обвешивать вызовы стартера аспектами Spring AOP.
   Разбора вариантов не было, и цены механизма никто не считал. Изменение аддитивное, поэтому
   ничего не блокирует и ждёт первого реального применения.

Закрытые вопросы из этого списка ушли в ADR; их история — в [roadmap](docs/roadmap.md).
