# taskcomm

Spring Boot стартер для надёжной фоновой работы и обмена с внешними системами — на PostgreSQL,
который у вас уже есть. Без брокера, без Redis, без отдельного сервиса.

## Что это

Две вещи, которые обычно пишут в каждом приложении заново:

- **Задачи.** Вы описываете, что сделать над множеством объектов и как обработать один объект.
  Стартер хранит задачи в базе, раздаёт работу между экземплярами приложения, повторяет
  упавшее, делит работу на части и собирает результат.
- **Коммуникации.** Вы описываете, как отправить сообщение во внешнюю систему и как обработать
  пришедшее от неё. Стартер делает то же самое и вдобавок отсеивает дубли, связывает асинхронные
  ответы с запросами, ограничивает скорость и перестаёт слать в лежащую систему.

Задача и коммуникация пишутся в вашу транзакцию: появляются вместе с вашими данными и исчезают
вместе с ними при откате — outbox без отдельной таблицы и отдельного кода.

## Когда он нужен

- **Массовая обработка с повтором по одному объекту.** «Синхронизировать заказы за сутки»:
  упали сто из миллиона — повторятся сто, задача закончится с предупреждением, упавшие можно
  перезапустить.
- **Надёжный вызов внешней системы.** Отправка в службу доставки с повторами, отказными
  статусами, ограничением скорости и размыкателем; в истории — что ушло и что вернулось на каждой
  попытке.
- **Приём вебхуков и сообщений.** Быстро ответить «принято», обработать надёжно, повторную
  доставку отсеять.
- **Асинхронные ответы.** Отправили заявку, через час пришёл результат с номером — он находит
  свой запрос сам.
- **Отложенное действие.** «Напомнить через сутки, если пользователь не подтвердил почту».

## Возможности

- Три формы задачи: неделимая, с подзадачами, с группами подзадач — когда группе нужны общие
  данные, полученные одним запросом.
- Подзадача — единица работы и повтора; результаты детей сводятся в результат родителя потоком,
  без загрузки в память.
- Коммуникации по транспортам — REST, SOAP, Kafka и сырой текст; вход и выход через один
  процессор на внешнюю систему.
- Синхронный и асинхронный приём входящих, асинхронные ответы по ключу корреляции.
- Дедупликация: по всей истории и по последнему успешно отправленному значению.
- Аренда с heartbeat, предел обработки, повторы с экспоненциальной паузой и обязательным
  случайным сдвигом.
- Приоритеты без голодания, выделенные очереди для шумных типов.
- Отмена и перезапуск на любом уровне — без потери истории попыток.
- Дело — всё, что произошло вокруг одного повода, одним запросом, с тем, кто кого создал.
- Горизонтальное масштабирование без настройки, партиционирование и очистка по времени.
- REST API для экранов сопровождения, поиск по полям нагрузки, метрики Micrometer, health indicator.

## Чем отличается от аналогов

|                      | Что это в первую очередь                                           | Чем отличается taskcomm                                                                                                |
|----------------------|--------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------|
| Quartz, db-scheduler | Планировщики: запуск по расписанию и однократный запуск в кластере | Нет расписаний, зато есть деление на подзадачи, сборка результата, коммуникации                                        |
| JobRunr              | Фоновые задачи из вызовов методов, с дашбордом                     | Задача — типизированная нагрузка и процессор, а не сериализованный вызов; три уровня работы; коммуникации              |
| Spring Batch         | Пакетная обработка: чтение — обработка — запись, перезапуск шагов  | Повтор и перезапуск — на уровне одного объекта; работа раздаётся экземплярам приложения без отдельного запуска заданий |
| Библиотеки outbox    | Доставка событий из базы в брокер                                  | Не нужен брокер: обработку выполняет само приложение, а обмен с внешней системой хранится целиком                      |

**Чего у taskcomm нет**, чтобы не искать:

- расписаний и cron — только однократная отсрочка;
- exactly-once — только at-least-once, процессоры обязаны быть идемпотентными;
- гарантии порядка выполнения;
- поддержки других баз, кроме PostgreSQL;
- собственного UI — только REST API для вашего;
- приёмного endpoint для входящих — их создаёт ваш контроллер или слушатель;
- защиты своего REST — пути закрываете вы.

## Пример за минуту

```groovy
implementation platform('xyz.avasilev:taskcomm-bom:2.0.0')
implementation 'xyz.avasilev:taskcomm-spring-boot-starter'
runtimeOnly 'org.postgresql:postgresql'
```

```java
@Component
public class MonthlyReport implements FlatTaskProcessor<YearMonth, ReportSummary> {

    @Override
    public String taskType() {
        return "monthly-report";
    }

    @Override
    public ReportSummary process(Task<YearMonth> task, ProcessingContext context) {
        return reports.build(task.payload());
    }
}
```

```java
@Transactional
public void close(YearMonth month) {
    ledger.close(month);
    taskService.submit(MonthlyReport.class, month);   // уйдёт в работу после коммита
}
```

Схема базы, первая коммуникация и проверка — в [быстром старте](docs/guide/start/quick-start.md).

## Статус и версии

Текущая версия — `2.0.0`. Задачи, коммуникации, REST и наблюдаемость готовы; публикация
в репозиторий артефактов ещё не настроена — пока сборка ставится только в локальный Maven
(`gradlew publishToMavenLocal`). Что дальше — [roadmap](docs/roadmap.md).

Версии — по semver: мажорная поднимается только при потере обратной совместимости. Свойства
и API не удаляются сразу — сначала помечаются устаревшими с указанием замены. Совместимость
стартера — это ещё и совместимость **ваших** данных: какие изменения в вашем коде ломают уже
записанные задачи, — в [Совместимости](docs/guide/evolution/compatibility.md).
