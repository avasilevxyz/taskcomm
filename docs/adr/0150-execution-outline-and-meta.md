# 0150. Дело без подзадач, счётчики подзадач и описание экземпляра

- **Дата:** 2026-11-12
- **Статус:** принято
- **Изменено:** [0153](0153-ui-creation-refinements.md) — в `/meta` приоритет по умолчанию у типов и систем и признак ручного приёма.
- **Изменено:** [0154](0154-ui-shell.md) — в `/meta` есть имя экземпляра.
- **Изменено:** [0159](0159-processor-title-and-description.md) — в `/meta` у типа и системы название и описание.

## Контекст

Интерфейс ([0149](0149-web-interface-module.md)) стоит только на REST, и трёх вещей в REST ему
не хватает.

**Дело.** `GET /executions/{id}` отдаёт дело целиком, без предела ([0140](0140-rest-controllers.md)),
и это сознательно: миллион подзадач — миллион строк в ответе. Программе, которой нужно всё, это
годится; браузеру — нет. При этом на экране дела нужны все задачи, группы и коммуникации с рёбрами,
а от подзадач — сколько их у каждого родителя в каком статусе, и сами подзадачи — страницами по клику.

**Прогресс.** Сводка ([0138](0138-inspection-api.md)) считает по типам во всём окне, а не по одному
родителю. Сколько подзадач задачи уже выполнено, из API чтения не узнать, не прочитав их все.

**Что можно создать.** Форме создания нужны типы задач и внешние системы, у которых есть процессор.
Сводка их не даёт: тип без единой сущности в окне в ней не появится, а осиротевший появится.
Ещё интерфейсу нужно знать, какие подсистемы включены, окно по умолчанию и версию стартера.

## Рассмотренные варианты

### Дело

- **Предел на выдачу целиком с признаком усечения.** Уже отвергнут в [0140](0140-rest-controllers.md):
  усечённое дело неотличимо от целого, если признак не прочитали.
- **Собирать дело на клиенте из списков с фильтром по делу.** REST не меняется, но счётчики подзадач
  по родителю так не получить, не прочитав подзадачи целиком. Отвергнуто.
- **Отдельная выдача дела без подзадач — выбрано:** задачи, группы, коммуникации, ключи корреляции
  и счётчики подзадач по родителю и статусу. Сами подзадачи — существующим списком
  `GET /tasks?level=UNIT` с делом и родителем, страницами. Выдача дела целиком остаётся как была.

### Где считаются подзадачи

- **В контроллере, перебором страниц.** Ровно то, от чего уходим. Отвергнуто.
- **Метод API чтения задач — выбрано:** `TaskInspection.unitCounts(ExecutionRef)` и запись
  `TaskUnitCount`. Один `GROUP BY` в партиции дела по индексу `(execution_id)`. Счётчик годится
  и потребителю со своим UI, и карточке задачи вне экрана дела.

### Откуда типы и системы

- **Из сводки.** Не те множества: см. контекст. Отвергнуто.
- **Из внутреннего реестра процессоров.** `rest` зависит только от `api`
  ([0087](0087-architecture-rules.md)). Отвергнуто.
- **Из бинов процессоров — выбрано.** Это публичные типы, у каждого есть `taskType()`
  или `externalSystem()`, форма контракта и транспорт — его тип. Реестр собран из тех же бинов,
  и два процессора одного имени до выдачи не доживают: стартер падает при старте.

### Одна выдача или по подсистемам

- **`/tasks/meta` и `/communications/meta`.** Интерфейс при старте делает два запроса, а версия
  и окно — общие и легли бы в оба. Отвергнуто.
- **Одна выдача `GET /meta` — выбрано.** Выключенная подсистема в ней отсутствует.

## Решение

- `GET /executions/{id}/outline` (необязательный `createdAt`, как у выдачи целиком): дело, задачи,
  группы и коммуникации в порядке создания, ключи корреляции и **счётчики подзадач** — строки
  «задача, группа, статус, число», группа пуста у подзадач без групп. Подзадач в выдаче нет.
- `TaskInspection.unitCounts(ExecutionRef)` → `List<TaskUnitCount>`; чтение в партиции дела, окно
  к нему не применяется — как у любого чтения в одном деле ([0138](0138-inspection-api.md)).
- `GET /meta`: версия стартера из манифеста jar (`Implementation-Version`; при запуске из классов
  её нет, и поле отсутствует), окно `taskcomm.rest.search-window` строкой ISO-8601, у включённой
  подсистемы задач — типы с формой контракта (`FLAT` | `UNIT` | `BATCH`), у коммуникаций — внешние
  системы с транспортом (`REST` | `SOAP` | `KAFKA` | `RAW`). Выключенной подсистемы в выдаче нет.
  Список вычисляется один раз при сборке контроллера: процессоры — синглтоны и в работе не меняются.

## Последствия

- В публичном API — новый метод `TaskInspection` и новая запись. Интерфейс реализует стартер, как
  и все интерфейсы чтения ([0138](0138-inspection-api.md)); моки потребителя не ломаются, а своя
  реализация `TaskInspection` у потребителя перестанет компилироваться — это не контракт, который
  потребителю предлагают реализовывать.
- Группы и коммуникации в выдаче без подзадач по-прежнему без предела. Граница проведена по подзадачам,
  потому что их число растёт с данными потребителя, а групп и коммуникаций в деле — с его логикой.
  Дело с сотней тысяч коммуникаций браузер не покажет, и это известная цена.
- Счёт подзадач миллионного дела — чтение миллиона строк по индексу: секунды, а не миллисекунды.
  Это чтение экрана, не горячий путь, и интерфейс обязан не повторять его чаще, чем раз в несколько
  секунд.
- Имени экземпляра в `meta` нет: оно внутреннее для движков, а там, где оно важно, — в состоянии
  размыкателей — выдача уже называет экземпляр.
- В jar `taskcomm-autoconfigure` появляются `Implementation-Title` и `Implementation-Version`.
