# 0144. Собственный BOM taskcomm: явный список версий

- **Дата:** 2026-11-06
- **Статус:** принято

## Контекст

Стартер везёт только обязательное: `spring-boot-starter`, `spring-boot-starter-jdbc`,
`spring-boot-starter-jackson`. Всё остальное потребитель добавляет сам, и версию тоже выбирает
сам: драйвер PostgreSQL, `spring-webmvc` и `spring-security-web` для REST
([0140](0140-rest-controllers.md)), `micrometer-core` и `spring-boot-health` для наблюдаемости
([0141](0141-observability-instance.md)), `jackson-dataformat-xml` для SOAP
([0135](0135-communication-engine.md)). Ответа на вопрос «какие версии к стартеру подходят»
у потребителя нет — его знает только сборка стартера.

[0001](0001-module-layout.md) отложил собственный BOM до второго независимо подключаемого
артефакта, исходя из того, что BOM согласует версии **наших** артефактов. Нужда оказалась другой:
согласовать с стартером версии **чужих** библиотек, которые он не везёт.

[0106](0106-starter-does-not-export-bom.md) запретил публиковать платформу из любого модуля.
Вред, который он устранял, — платформа, приезжающая **транзитивно** со стартером: Gradle-потребитель
её не просил, а версии у него поднимались. BOM, который потребитель подключает сам, этого
свойства не имеет.

## Рассмотренные варианты

### A. Отдельный модуль `taskcomm-bom` с явным списком — выбрано

`java-platform` с ограничениями версий на наши два артефакта, прямые зависимости стартера
и необязательные зависимости из перечня выше. Версии необязательных вычисляются при сборке
из BOM Spring Boot, на котором собран стартер, — каталог их не дублирует. Чужие библиотеки
вне списка BOM не трогает.

### B. BOM с импортом `spring-boot-dependencies` — отвергнуто

Короче, но фиксирует сотни библиотек, которых стартер не касается, — по сути BOM Spring Boot
под нашим именем. Это то навязывание, от которого уходил [0106](0106-starter-does-not-export-bom.md),
только с шагом подключения.

### C. «Полный» стартер, который тянет всё необязательное — отвергнуто

BOM в строгом смысле ничего не подтягивает. Стартер, тянущий MVC, Security и Actuator, навязал
бы потребителю Tomcat и цепочку фильтров Security и отменил бы решения
[0135](0135-communication-engine.md), [0140](0140-rest-controllers.md),
[0141](0141-observability-instance.md) о том, что эти функции включает сам потребитель.

### D. Таблица версий в документации — отвергнуто

Разойдётся с кодом при первом же обновлении Spring Boot; проверить её сборкой нельзя.

## Решение

- **Модуль `taskcomm-bom`**, плагин `java-platform`, публикуется как `xyz.avasilev:taskcomm-bom`
  с той же версией, что и остальные модули.
- **Состав — явный и закрытый**: `taskcomm-autoconfigure`, `taskcomm-spring-boot-starter`, прямые
  зависимости стартера и необязательные зависимости из контекста. Импорта чужих BOM и самих
  зависимостей в нём нет — только ограничения версий. Новая необязательная зависимость стартера
  добавляется в список вместе с решением, которое её вводит.
- **Проверка — задача `verifyBom`** в составе `check` модуля. Она читает опубликованные `.module`
  и `.pom` BOM и стартера и падает, если BOM объявляет зависимость, импортирует чужой BOM или
  не содержит какой-то зависимости стартера с той же версией.
- `verifyNoExportedPlatform` из [0106](0106-starter-does-not-export-bom.md) остаётся на библиотечных
  модулях: BOM — единственный модуль, публикующий платформу, и он не приезжает транзитивно.

## Последствия

- **Потребитель подключает BOM и пишет зависимости без версий** — стартер и любые необязательные
  из списка. Подключать BOM не обязательно: стартер по-прежнему самодостаточен.
- **Gradle-потребитель, подключивший BOM через `platform`, получает подъём перечисленных библиотек
  до наших версий.** Это его выбор, а не побочный эффект стартера; `enforcedPlatform` опустил бы
  их и вниз — тоже его выбор.
- **Maven-потребитель с `spring-boot-starter-parent` получит наши версии поверх версий Boot**
  для перечисленных библиотек, если импортирует BOM в `dependencyManagement`: так работает импорт.
  На той же версии Spring Boot версии совпадают.
- **Сборка BOM разрешает граф BOM Spring Boot при конфигурации проекта** — только метаданные,
  без jar.
- **Liquibase в BOM нет**: стартер от него не зависит, changelog совместим с ветками 4 и 5
  ([0092](0092-jackson-3-liquibase-compatibility.md)), и выбор версии остаётся за потребителем.

## Связанные решения

- [0001](0001-module-layout.md) — откладывал собственный BOM; этим решением он заведён по другой
  причине.
- [0106](0106-starter-does-not-export-bom.md) — запрет платформы сужен до библиотечных модулей.
- [0135](0135-communication-engine.md), [0140](0140-rest-controllers.md),
  [0141](0141-observability-instance.md) — необязательные зависимости, версии которых фиксирует BOM.
