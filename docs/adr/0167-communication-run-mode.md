# 0167. Режим запуска коммуникации и синхронная отправка исходящей

- **Дата:** 2026-11-16
- **Статус:** принято

## Контекст

Раскрытию задачи бывает нужен ответ внешней системы: на какие группы делить, видно только из него.
Ждать коммуникацию в `expand` нельзя — исходящая только встаёт в очередь и уйдёт после того, как
раскрытие закончится. Процессор задачи работает вне транзакции, а синхронный приём входящей
([0133](0133-synchronous-inbound-reception.md)) уже умеет создать коммуникацию и обработать её в потоке
вызывающего. Того же не хватало исходящей.

Синхронный приём держался без признака режима ([0074](0074-uniform-communication-processing.md)):
переподхват не отличал синхронную коммуникацию от прочих, и от фонового повтора её защищало требование
к потребителю — `max-attempts: 1`, стартером не проверяемое. Для синхронной отправки этого мало:
повторять её в потоке по настройкам системы и при этом не повторять фоном можно, только если движок
знает, что коммуникацию ведёт вызывающий.

## Решение

### Режим запуска в схеме

- Колонка `tc_communication.run_mode`: `SYNC` | `ASYNC`, по умолчанию `ASYNC`. Это **режим запуска**,
  свойство вызова, а не коммуникации и не процессора; имя не `execution_mode` — `execution_*` в схеме
  означает дело. В API — перечисление `RunMode` и `CommunicationSnapshot.runMode()` (`default` — `ASYNC`).
- **Захват синхронные не берёт**: условие `run_mode = 'ASYNC' OR phase = 'HANDLE_RESPONSE'` —
  колбэк синхронной обрабатывает движок, как у любой. Индексы захвата — **новые частичные** с тем же
  условием; прежние остаются до следующего выпуска, по ним ходят экземпляры старой версии во время
  поэкземплярного обновления.
- **Фоном синхронную не повторяют.** Вызывающий умер посреди попытки — переподхват закрывает её
  `LEASE_LOST`, коммуникацию — `FAILED`. Умер в паузе между попытками — открытую незахваченную
  попытку никто не возьмёт, и синхронную `PENDING`, чей срок прошёл больше чем на аренду, закрывает
  `FAILED` подстраховочный поллер. Истёк срок ожидания колбэка — `FAILED` без повторной отправки.

### Синхронная отправка

- `CommunicationService.sendAndProcess(система, запрос[, SyncSendOptions])` — `default`-методы.
  Коммуникация создаётся своей короткой транзакцией, сразу с попыткой под арендой этого экземпляра,
  процессор вызывается воркером движка под heartbeat. Внутри активной транзакции — исключение
  до записи, как у синхронного приёма.
- **Повторы — в потоке вызывающего, по настройкам повторов системы**: неуспех закрывается как у любой
  попытки, решение о повторе прежнее, а паузу ждёт и следующую попытку забирает сам вызывающий.
  Число попыток и паузы задаёт потребитель; `max-attempts: 1` — без повторов.
- **Размыкатель и ограничитель скорости** — поток ждёт их не дольше предела: `SyncSendOptions.syncWait`
  или свойство `sync-wait` (глобально, у системы в `yaml` и в `@CommunicationProcessorSettings`),
  по умолчанию **30 с**. Наступила проба разомкнутого — вызов сам становится пробой. Истёк предел
  до первой попытки — `Unavailable`, коммуникация **не создаётся**; перед повтором — `FAILED`.
- **Колбэк — решает вызов**: по умолчанию вызов возвращается с синхронным ответом, колбэк обработает
  движок; с `awaitResponse(предел)` поток ждёт его опросом строки — `Responded` или `Awaiting`.
- Итог — запечатанный `SendAndProcessResult`: `Processed`, `Responded`, `Awaiting`, `Failed`,
  `Duplicate`, `Unavailable`. «Не раньше» у синхронной отправки не бывает — исключение.

### Синхронный приём

- Пишет `run_mode = 'SYNC'` и **повторяется в потоке по настройкам системы**, как отправка.
  Требование `max-attempts: 1` снимается: от фонового повтора защищает режим.

### Ручной перезапуск

- **Синхронную исходящую не перезапускают**: ответ ждал вызывающий здесь и сейчас, перезапускать её
  некому — отказ с причиной.
- **Синхронную входящую перезапускают**: данные запроса у нас, перезапуск ставит её в фоновую
  обработку — `run_mode` становится `ASYNC`.

## Рассмотренные варианты

- **Без колонки: одна попытка в потоке, повторяет раскрытие задача.** Требование `max-attempts: 1`
  к потребителю остаётся, повторов в потоке нет. Отвергнуто: потребитель хочет повторять синхронный
  вызов по настройкам системы, а без признака режима переподхват повторил бы его фоном.
- **Две задачи через коммуникацию** — отправить, а раскрыть вторую задачу по ответу. Работает без
  правок стартера, но раскрытие формально принадлежит второй задаче, а ответ едет в её нагрузке.
- **Раскрытие ждёт коммуникацию без аренды** — новый статус задачи и переход. Одна задача без занятого
  потока, но цена — жизненный цикл задачи, отмена, перезапуск и подстраховка. Не сейчас.
- **Фильтр режима без новых индексов.** Синхронная в `PENDING` бывает только в паузе между попытками,
  но синхронно может запускаться почти всё — потребитель выбрал индексы.

## Последствия

- Изменены [0074](0074-uniform-communication-processing.md) (колонка режима есть),
  [0133](0133-synchronous-inbound-reception.md) (повторы в потоке, требование `max-attempts: 1` снято),
  [0086](0086-async-response-in-outbound.md) (истёкшее ожидание синхронной — `FAILED` без повторной
  отправки), [0137](0137-rate-limit-and-circuit-breaker.md) (синхронная отправка ждёт защиту в потоке),
  [0139](0139-restart-api.md) (перезапуск по режиму).
- Миграция `taskcomm-2.3.0.sql` строит индексы захвата по всем партициям под блокировкой записи
  в таблицу: на партиционированной таблице `CONCURRENTLY` нет. Окно обновления планируется по размеру.
- Пока идёт поэкземплярное обновление, экземпляры старой версии фильтра режима не знают и могут взять
  синхронную коммуникацию в паузе между попытками.
- Синхронный приём у тех, кто держал у системы `max-attempts` больше одного ради фоновых повторов,
  теперь повторяется в потоке вызывающего — отправитель дольше ждёт ответа.
- Время синхронного вызова уходит из бюджета вызывающего: у раскрытия это предел обработки фазы.
