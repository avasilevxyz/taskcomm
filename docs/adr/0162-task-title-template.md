# 0162. Шаблоны названия задачи, группы и подзадачи

- **Дата:** 2026-11-13
- **Статус:** принято

## Контекст

Карточка задачи в интерфейсе называется названием процессора
([0159](0159-processor-title-and-description.md)): у всех задач типа оно одно — «Выгрузка
каталога». Различает их только идентификатор, а человеку нужно «Выгрузка каталога весна-2026»:
название со значением из нагрузки. В стопке боковых панелей ([0161](0161-side-panel-stack.md))
это особенно заметно — на свёрнутых полосах несколько одинаковых названий подряд.

## Решение

- В `TaskProcessor` — метод по умолчанию `taskTitle()`: шаблон названия одной задачи,
  например `"Выгрузка каталога {catalog}"`. По умолчанию `null` — задача называется `title()`.
- Подстановка `{имя}` — **поле поиска уровня задачи** из `searchableTaskFields()`. Интерфейс берёт
  значение по пути поля из реестра в нагрузке задачи — так же, как колонки полей поиска в таблице.
  Значения в нагрузке нет — прочерк.
- Подстановка не из полей поиска уровня задачи — **падение при старте**
  `TaskcommConfigurationException`, в реестре процессоров: молча пустое название хуже ошибки.
- Шаблон — оформление: в базу не пишется, правится на месте. `/meta` отдаёт шаблоны у типа
  объектом `titleTemplates` — `task`, `batch`, `unit`.
- Так же у групп и подзадач: `batchTitle()` в `BatchTaskProcessor`, `unitTitle()`
  в `UnitTaskProcessor` и `BatchTaskProcessor`. Подстановки — поля поиска **своего** уровня:
  `searchableBatchFields()` и `searchableUnitFields()`; не из них — тоже падение при старте.
  Шаблон задачи — её полное название, а шаблон группы или подзадачи — **уточнение**: интерфейс пишет
  его после названия процессора — «Выгрузка каталога · Поставщик 3, Новосибирск», — иначе
  пропадает, частью чего группа или подзадача является.
  У контракта без такого уровня поля в `titleTemplates` нет.
- У коммуникаций реестра полей поиска нет (CLAUDE.md, открытый вопрос № 2), подставлять нечего.

## Рассмотренные варианты

- **Признак у `SearchableField`** — «поле входит в название». Отвергнуто: `SearchableField` —
  публичная запись, новый компонент меняет её канонический конструктор и ломает разбор по шаблону
  у потребителя; признак пришлось бы хранить в реестре в базе — новая колонка и миграция; порядок
  слов не задать — «Сверка выписки по счёту …» не собрать.
- **Метод процессора, который строит название из нагрузки в Java.** Отвергнуто: название пришлось
  бы считать на сервере для каждой строки — разбирать нагрузку при каждом чтении — или хранить
  колонкой, которая устаревает вместе с кодом.
- **Подстановка по произвольному пути JSON.** Отвергнуто: путь разбирался бы вторым способом рядом
  с реестром полей поиска, а поле поиска уже даёт проверенный путь и подпись.

## Последствия

- Изменение аддитивное: методы по умолчанию в публичных контрактах и поля в `/meta`.
- Чтобы значение попало в название, поле должно быть объявлено полем поиска. Это не ограничение
  на практике — в название идут те же идентификаторы, по которым ищут.
