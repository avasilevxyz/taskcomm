# 0138. Публичный API чтения задач и коммуникаций

- **Дата:** 2026-11-05
- **Статус:** принято

## Контекст

Этап 6 — REST ([0014](0014-rest-api.md), [0091](0091-rest-disabled-by-default.md)). Состав чтения
задан правилами: списки и детали с фильтрами по статусам, поиск по нагрузке по реестру полей
([0037](0037-search-field-registry.md)), список полей для UI, сводка по типам и признак осиротевшей
сущности ([0105](0105-orphan-communications.md)), история попыток с обменом и лукап по `request_id`
([0055](0055-communication-exchange-storage.md)), состояние размыкателей экземпляра
([0065](0065-communication-circuit-breaker.md)), окно чтения истории
([0101](0101-active-partition-horizon.md)).

Ограничения, которые нельзя обойти: `rest` зависит только от `api`
([0087](0087-architecture-rules.md)), задачи и коммуникации друг о друге не знают, `execution`
не знает ни о тех, ни о других. Контроллер поэтому не может читать таблицы сам — ему нужен
публичный API чтения, и тот же API пригоден потребителю, у которого свой UI.

Этап нарезан на три части: 6a — API чтения и его реализация, 6b — запись (отмена коммуникаций,
перезапуск по [0071](0071-no-restart-after-cancel.md), [0097](0097-no-restart-during-collect.md),
[0098](0098-restart-only-latest-expansion.md), ручное удаление результатов), 6c — контроллеры, DTO,
`RequestMatcher` и автоконфигурация. Здесь — решения 6a.

## Рассмотренные варианты

### Где живёт чтение

- **Контроллеры читают таблицы напрямую.** Нарушает границу `rest → api`, и потребитель без REST
  остаётся без чтения. Отвергнуто.
- **Один общий сервис чтения.** Ему пришлось бы зависеть и от задач, и от коммуникаций; положить его
  некуда — `execution` пассивен и о подсистемах не знает. Отвергнуто.
- **Свой сервис у каждой подсистемы — выбрано:** `TaskInspection` и `CommunicationInspection`.
  Чтение — отдельный интерфейс, а не методы `TaskService` и `CommunicationService`: сервисы
  создания вызывает код потребителя в бизнес-транзакциях, чтение нужно экранам и сопровождению,
  и смешивать их — раздувать контракт, который потребитель мокает в своих тестах.

### Общие значения запроса и выдачи

Окно, страница и запрос страницы одинаковы у обеих подсистем, а общего кода у подсистем быть
не должно.

- **Свои копии в каждой подсистеме.** Две пары одинаковых типов в публичном API, и REST
  переводил бы одно в другое. Отвергнуто.
- **В `execution.api` — выбрано:** `HistoryWindow`, `PageRequest`, `Page`. Это значения без
  поведения подсистем; `execution` от них ни от чего не начинает зависеть, а подсистемы и так
  зависят от `execution.api`. Реализация разбора курсора при этом своя у каждой подсистемы —
  общего кода нет.

### Страницы

- **Смещение (`OFFSET`).** На партиционированных таблицах с поиском по нагрузке каждая следующая
  страница дороже предыдущей, а вставки между запросами сдвигают выдачу — строки повторяются
  или пропадают. Отвергнуто.
- **По ключу — выбрано.** Порядок от новых к старым по `(execution_created_at, created_at, id)`,
  курсор — непрозрачная строка с ключом последней строки, следующая страница — сравнение строк
  `(…) < (…)`. Первый элемент ключа — ключ партиционирования: старые партиции отсекаются,
  как только курсор ушёл за их диапазон. Цена — нет «перейти на страницу N» и нет общего числа
  строк; число даёт сводка.

### Форма снимка

- **Доменные формы, восстановленные по дженерику процессора.** У осиротевшего типа процессора
  нет — восстановить нечем, а показывать такие сущности обязательно. Ещё и REST сериализовал бы
  обратно то, что только что разобрали. Отвергнуто.
- **Снимки с сырым JSON нагрузки — выбрано.** `TaskSnapshot`, `CommunicationSnapshot`
  и снимки попыток — интерфейсы, как `Task` и `Communication`: новое поле не ломает
  совместимость ([0134](0134-communication-public-api-shape.md)). Статусы задач в снимке —
  строкой: перечисления статусов у уровней свои, а снимок общий для трёх уровней.

### Окно в Java API

- **Окно по умолчанию внутри сервиса.** Сервис молча ограничивал бы выдачу, и «не нашлось»
  у потребителя значило бы разное в зависимости от свойства. Отвергнуто.
- **Окно — обязательный параметр каждого чтения истории — выбрано.** «Искать везде» —
  явное `HistoryWindow.everywhere()`. Умолчание `taskcomm.rest.search-window` применяет REST,
  а выдача называет окно, в котором искали. Чтение в одном деле идёт в его партиции, и окно
  к нему не применяется.

### Поле поиска, которое никто не объявил

Ошибка — `UnknownSearchFieldException`, наследник `TaskcommException` в `task.api`, со списком
известных имён уровня. REST переводит его в `400`. Пустой результат вместо исключения отвергнут:
опечатка в имени поля неотличима от «таких нет».

## Решение

- `task.api`: `TaskInspection` — `list`, `find`, `attempts`, `searchableFields`, `summary`;
  `TaskQuery`, `TaskSnapshot` с уровнем, `TaskAttemptSnapshot`, `SearchableFieldSnapshot`,
  `TaskTypeSummary`, `UnknownSearchFieldException`.
- `communication.api`: `CommunicationInspection` — `list`, `find`, `attempts`, `correlationKeys`,
  `circuitBreakers`, `summary`; `CommunicationQuery` с фильтром по `request_id`,
  `CommunicationSnapshot`, `CommunicationAttemptSnapshot` с обменом, `CorrelationKeySnapshot`,
  `CircuitBreakerSnapshot`, `CommunicationSummary`.
- `execution.api`: `HistoryWindow`, `PageRequest` (размер от 1 до 1000), `Page`.
- Поиск по нагрузке собирается из реестра: типы, объявившие все поля; по каждому полю — `OR`
  по объявлениям; ветка `NUMBER` отбрасывается, если значение не число, и сравнивается через
  приведение только тогда, когда текст поля — число. Однословный путь даёт выражение
  `payload ->> 'имя'` — то, которое обслуживает частичный индекс из правил.
- Размыкатели — только этого экземпляра, с его именем; система попадает в выдачу, когда у неё
  заведён размыкатель.
- Бины — без условий, в автоконфигурациях своих подсистем.

## Последствия

- Публичный API вырос на два сервиса и полтора десятка типов; всё это теперь под обязательствами
  совместимости.
- Нет перехода на произвольную страницу и общего числа строк в списке.
- Найти сущность по одному идентификатору без окна нельзя: идентификатор не ключ партиционирования,
  и «везде» — явный обход всех партиций.
- Сводка — точный `count(*)` по окну; на больших окнах это полный проход по партициям окна.
- Состояние размыкателей других экземпляров не видно: синхронизации нет
  ([0065](0065-communication-circuit-breaker.md)).
