# 0149. Веб-интерфейс: отдельный модуль поверх REST

- **Дата:** 2026-11-12
- **Статус:** принято
- **Изменено:** [0151](0151-default-paths-under-tc.md) — путь интерфейса по умолчанию `/tc`, REST — `/tc/api`.

## Контекст

REST готов ([0014](0014-rest-api.md), [0091](0091-rest-disabled-by-default.md),
[0138](0138-inspection-api.md)–[0140](0140-rest-controllers.md)), а интерфейса для человека нет:
правила везде говорят «UI потребителя». Разбирать упавшую задачу через `curl` можно, но то, чем
taskcomm богаче похожих библиотек, — дело с рёбрами «кто кого создал», обмен коммуникации
по попыткам, иерархия задача → группа → подзадача с фазами — без интерфейса не увидеть.

Ограничения, которые нельзя обойти: стартер не навязывает потребителю поведение (CLAUDE.md, «Правила
стартера»), не трогает Spring Security ([0014](0014-rest-api.md)), не регистрирует бинов чужих типов,
которые потребляет сам, и сверх двух отдаваемых их не заводит ([0096](0096-no-foreign-type-beans.md)),
не требует новой инфраструктуры ([0077](0077-external-infrastructure-optional.md)); каждая зависимость
стартера приезжает всем потребителям.

Похожие библиотеки решают это по-разному:

- **db-scheduler-ui** — отдельный Spring Boot starter, SPA в jar, свой путь; безопасность на приложении.
- **JobRunr** — свой HTTP-сервер на отдельном порту и своя basic-auth.
- **Camunda Cockpit** — отдельный модуль со статикой в jar и своей моделью пользователей.
- **Hangfire, Sidekiq Web** — монтируются в приложение по пути, авторизацию решает приложение.
- **Temporal UI, Conductor UI, Spring Boot Admin** — отдельное приложение против API.
- **Quartz** — интерфейса нет.

## Рассмотренные варианты

### Где живёт интерфейс

- **Не делать.** Честно, но всё, ради чего заводились сводка, признак осиротевшей сущности, подписи
  полей поиска и дело целиком, остаётся невидимым без своего UI у каждого потребителя. Отвергнуто.
- **Внутри `taskcomm-autoconfigure`.** Сотни килобайт статики едут каждому потребителю, включая тех,
  у кого REST выключен. Отвергнуто.
- **Свой HTTP-сервер на отдельном порту**, как у JobRunr. Ещё один сервер, порт и своя авторизация
  в чужом приложении — ровно то, что стартер делать не вправе. Отвергнуто.
- **Отдельное приложение** против REST нескольких сервисов. Новая инфраструктура у потребителя,
  CORS и своя авторизация между двумя приложениями. Отвергнуто.
- **Отдельный модуль `taskcomm-ui` — выбрано**, как db-scheduler-ui. Подключается явно, приезжает
  только тому, кто подключил, и живёт в приложении по пути, как Hangfire: кого пускать, решает
  конфигурация безопасности потребителя.

### Как написан

- **Серверный рендер** (Thymeleaf, JTE). Новая рантайм-зависимость у потребителя ради страниц
  стартера. Отвергнуто.
- **JavaScript без сборщика.** Node в сборке не нужен, но без типов и тестов экраны с десятком
  фильтров и деревом дела быстро становятся хрупкими. Отвергнуто.
- **Preact.** Легче, но слой совместимости с компонентами React — лишняя точка отказа. Отвергнуто.
- **SPA на React и TypeScript, сборка Vite — выбрано.** Итог — только статика, рантайм-зависимостей
  у потребителя ноль. Node скачивает плагин Gradle сам, ставить его на машину и в CI не нужно.

### Как раздаётся статика

- **В `static/` или `META-INF/resources/` jar.** Spring Boot сам раздал бы её с корня приложения —
  пути стартера у потребителя, которых он не заказывал. Отвергнуто.
- **Бином `WebMvcConfigurer` с обработчиком ресурсов.** Бин чужого типа, который потребляет Spring MVC, —
  третий отдаваемый бин сверх двух, перечисленных в правилах. Отвергнуто.
- **Внутренним контроллером — выбрано**, как контроллеры REST: бин внутреннего типа, статика —
  в `META-INF/taskcomm/ui/` jar. Контроллер отдаёт `index.html` на любой путь экранов, ассеты
  с хешем в имени — с долгим кешем, и подставляет в `index.html` пути UI и REST.

### Какие данные читает

- **Свой API для интерфейса.** Второй контракт с теми же данными. Отвергнуто.
- **Только существующий REST — выбрано.** Чего не хватает, добавляется в REST и годится любому
  клиенту ([0150](0150-execution-outline-and-meta.md)).

## Решение

- Модуль **`taskcomm-ui`**: статика SPA в `META-INF/taskcomm/ui/`, своя автоконфигурация со своим
  `AutoConfiguration.imports`, в `taskcomm-bom`. В стартер не входит.
- Условия: servlet-приложение со Spring MVC, корневой выключатель, **включённый REST**
  (`taskcomm.rest.enabled: true`, [0091](0091-rest-disabled-by-default.md)) и `taskcomm.ui.enabled`.
- **`taskcomm.ui.enabled` по умолчанию `true`.** Подключить модуль — уже явный шаг, а без REST
  интерфейс всё равно не появляется, так что второго выключенного по умолчанию свойства не нужно.
- **`taskcomm.ui.base-path` по умолчанию `/taskcomm`** — не пересекается с REST
  (`/api/taskcomm` по умолчанию).
- **Пути UI закрывает тот же `taskcommRequestMatcher`**, нового отдаваемого бина нет: свойства
  `taskcomm.ui.*` лежат в общем классе свойств, и сопоставитель добавляет путь UI, когда модуль
  на classpath и включён.
- Spring Security интерфейс не трогает. Изменяющие запросы шлют токен CSRF из cookie `XSRF-TOKEN`,
  если он есть; `403` показывается как «нет прав», а не как ошибка — так потребитель делит
  «смотреть» и «управлять» своими правилами по методам и путям.
- Объём: обзор (сводки, осиротевшие типы и системы, размыкатели), задачи, коммуникации, дело,
  отмена, перезапуск, удаление результатов и **создание задач и коммуникаций** из формы с JSON.
- Свежесть — опросом открытого экрана. Подписка на события — открытый вопрос, интерфейс её не ждёт.

## Последствия

- В сборке появляется Node: плагин Gradle скачивает его, и сборка модуля дольше и тяжелее остальных.
- REST становится контрактом между интерфейсом и сервером. Оба выпускаются одной версией и связаны
  BOM; интерфейс другой версии, чем стартер, не поддерживается.
- Подключённый модуль с включённым REST открывает экраны управления, как REST открывает пути:
  без Spring Security они доступны всем, кто достучится до порта. Это прямая цена
  [0014](0014-rest-api.md), и документация обязана сказать это крупно.
- Свойства `taskcomm.ui.*` видны в автодополнении и без модуля — плата за один сопоставитель путей.
- Создание из формы делает интерфейс способом отправить сообщение во внешнюю систему. Закрывать
  `POST` потребитель обязан так же, как закрывает его у REST.
