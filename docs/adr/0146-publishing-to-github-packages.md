# 0146. Публикация в GitHub Packages из GitHub Actions по тегу

- **Дата:** 2026-11-08
- **Статус:** принято
- **Изменено:** [0147](0147-publishing-to-maven-central.md) — выпуск идёт ещё и в Maven Central,
  отложенный здесь вариант C принят.

## Контекст

До сих пор артефакты публиковались только в локальный Maven-репозиторий (`publishToMavenLocal`).
Потребителю на другой машине взять стартер было неоткуда. Целевой репозиторий — Nexus,
но для него нет ни адреса, ни учётных данных. Исходники уже лежат на GitHub. CI нет вовсе:
полная сборка с интеграционными тестами запускается только локально, руками.

Ограничения:

- публиковать можно только то, что прошло полную сборку, включая интеграционные тесты
  на Testcontainers;
- учётные данные не должны попасть в репозиторий;
- версия выпуска однозначна: опубликованный релиз не переписывается.

## Рассмотренные варианты

### A. GitHub Packages, публикация из GitHub Actions по тегу — выбрано

Workflow на push тега `v*` сверяет тег с версией в `build.gradle`, гоняет полную сборку
и вызывает `publish`. Учётные данные — встроенный `GITHUB_TOKEN` с правом `packages: write`,
секретов заводить не надо. Плюсы: инфраструктура уже есть, публикует проверенная сборка, выпуск
привязан к тегу в истории. Минус: GitHub Packages требует токен даже на чтение публичного пакета.

### B. GitHub Packages, публикация с машины разработчика — отвергнуто

Нужен личный токен с правом записи на машине. Опубликовать можно сборку, которую никто
не проверил, и из рабочей копии, которой нет в истории.

### C. Сразу Maven Central — отложено

Читается без токена, это лучший вариант для широкого круга потребителей. Требует подтверждения
домена группы `xyz.avasilev`, подписи артефактов GPG и прохождения проверок Central Portal. Для
первого выпуска это лишняя работа; workflow из варианта A потом расширяется вторым репозиторием.

### D. Ждать Nexus — отвергнуто

Блокирует выпуск на неопределённый срок, а решение «откуда и чем публикуем» от адреса
репозитория не зависит.

## Решение

- **Репозиторий** — `https://maven.pkg.github.com/avasilevxyz/taskcomm`, объявлен в корневом
  `build.gradle` для всех модулей с `maven-publish`, включая `taskcomm-bom`.
- **Учётные данные — только из окружения**: `GITHUB_ACTOR` и `GITHUB_TOKEN`. Без них
  `publishToMavenLocal` работает как прежде, падает только `publish`.
- **Публикует workflow `publish.yml` по тегу `v<версия>`**: сверка тега с версией, полная сборка,
  публикация. Тег, не совпадающий с версией, валит workflow до сборки.
- **Workflow `build.yml`** гоняет полную сборку на каждый push и pull request — тот же
  `gradlew build`, что и локально.
- **К jar публикуются исходники и Javadoc**, в POM — лицензия MIT, адрес проекта и SCM.

## Последствия

- **Выпуск — это push тега.** Версия в `build.gradle` поднимается заранее, отдельным коммитом;
  повторно опубликовать ту же версию GitHub Packages не даст.
- **Потребителю нужен токен GitHub с правом `read:packages`** и объявление репозитория в своей
  сборке — даже для публичного пакета. Это главная цена варианта и причина вернуться
  к Maven Central или Nexus.
- **Сборка в CI идёт на Temurin 25 последнего патча**, локально — на сборке Microsoft. Проверка
  нижней границы JDK из [0088](0088-java-25-spring-boot-4.md) действует в обоих случаях.
- **Интеграционные тесты в CI идут на Docker раннера** — так, как требует
  [0085](0085-tests-on-real-postgres.md).
- Javadoc собирается и по пакетам `internal`: они в том же модуле, и отделить их без потери
  ссылок из `autoconfigure` нельзя. Предупреждения о недостающих комментариях там — не ошибка.
