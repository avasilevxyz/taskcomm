# 0147. Публикация в Maven Central своими средствами сборки

- **Дата:** 2026-11-08
- **Статус:** принято

## Контекст

С [0146](0146-publishing-to-github-packages.md) выпуск уходит в GitHub Packages. Тот отдаёт пакет
только с токеном GitHub, даже публичный. Каждому потребителю приходится заводить токен и объявлять
отдельный репозиторий. Тогда Maven Central был отложен: он требует подтверждённого namespace,
подписи артефактов и прохождения проверок портала.

Maven Central принимает выпуски через Central Portal. Портал ждёт архив: файлы компонентов
в раскладке Maven-репозитория, у каждого подпись `.asc` и контрольные суммы `.md5` и `.sha1`.
POM обязан содержать имя, описание, адрес проекта, лицензию, разработчиков и SCM. Выпущенную
версию из Central нельзя ни удалить, ни заменить.

Namespace — `xyz.avasilev`, как у group проекта: домен `avasilev.xyz` принадлежит автору,
и namespace подтверждается записью TXT в его DNS.

## Рассмотренные варианты

### A. Встроенные средства Gradle и Publisher API портала — выбрано

Плагин `signing` из поставки Gradle подписывает публикации ключом из окружения. `maven-publish`
кладёт их в file-репозиторий внутри `build`, и контрольные суммы он пишет сам. Задача `centralBundle`
пакует каталог в zip и проверяет, что подписан каждый файл. Workflow отправляет архив `curl`
в Publisher API и ждёт итога проверки. Плюсы: ни одного стороннего плагина, каждый шаг виден
в `build.gradle` и в workflow. Минус: около сорока строк своего кода сборки.

### B. Плагин `com.vanniktech.maven.publish` — отвергнуто

Умеет Central Portal сам, и своего кода меньше. Но это ещё одна сторонняя зависимость сборки
со своим циклом обновлений, а ради одной загрузки архива она не нужна.

### C. JReleaser — отвергнуто

Полноценный инструмент выпуска: заметки, анонсы, несколько площадок. Нам из этого нужна только
загрузка в Central, а настройки у него больше, чем весь вариант A.

### D. Совместимый с OSSRH Staging API — отвергнуто

Позволяет публиковать через `maven-publish` напрямую, но портал держит его как переходный
режим для старых сборок. Закрытие репозитория всё равно требует отдельного вызова API.

### E. Сменить namespace на `io.github.avasilevxyz` — отвергнуто

Подтверждается без DNS. Но меняет координаты всех артефактов, а версия 2.0.0 уже опубликована
под `xyz.avasilev`.

## Решение

- **Выпуск по тегу идёт в оба места**: GitHub Packages из [0146](0146-publishing-to-github-packages.md)
  остаётся, Maven Central добавляется.
- **Подпись — встроенный плагин `signing`**, ключ ASCII-armored в `SIGNING_KEY`, пароль
  в `SIGNING_PASSWORD`. Ключ задан — подпись обязательна. Не задан — пропускается, и локальная
  сборка с `publishToMavenLocal` работают как прежде.
- **Архив — задача `centralBundle`** в корневом `build.gradle`. Она публикует все модули
  в `build/central/staging`, предварительно очистив его, пакует без `maven-metadata`
  и падает, если хоть один `.jar`, `.pom` или `.module` не подписан.
- **Загрузка — шаг workflow `publish.yml`**: `POST /api/v1/publisher/upload` с
  `publishingType=AUTOMATIC`, затем опрос состояния до `PUBLISHING` или `PUBLISHED`. `FAILED` валит
  workflow и выводит ответ портала. Учётные данные — токен пользователя портала в секретах
  `CENTRAL_USERNAME` и `CENTRAL_PASSWORD`.
- **Загрузка в Central — последний шаг**: выпущенное там не отзывается, поэтому до неё доходит
  только то, что прошло сборку и опубликовано в GitHub Packages.
- **POM дополнен** описанием каждого модуля, разработчиком и `developerConnection`.

## Последствия

- **Потребителю достаточно `mavenCentral()`**, токен GitHub больше не нужен. GitHub Packages
  остаётся запасным источником.
- **Ошибка в выпуске неисправима** иначе как новой версией: Central не даёт удалить
  или заменить опубликованное.
- **Ключ подписи и токен портала — секреты репозитория.** Открытый ключ должен лежать на сервере
  ключей, иначе портал не проверит подпись. Срок действия ключа — забота автора: истёк — выпуски
  перестанут проходить.
- **GitHub Packages не принимает версию повторно.** Если workflow упал после публикации туда,
  перезапуск того же тега упадёт на ней. Версию в GitHub Packages придётся удалить вручную либо
  выпустить следующую.
- Портал проверяет архив несколько минут, и workflow ждёт до получаса. Появление в поиске
  Central занимает ещё дольше, этого workflow не ждёт.
