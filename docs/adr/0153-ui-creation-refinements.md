# 0153. Создание из интерфейса: дело по идентификатору, ручной приём входящих, приоритет по умолчанию

- **Дата:** 2026-11-12
- **Статус:** принято
- **Изменено:** [0161](0161-side-panel-stack.md) — боковые панели стопкой рядом друг с другом, а не Drawer поверх.
- **Изменено:** [0163](0163-create-in-execution-only-on-execution.md) — «Создать в этом деле» только на экране дела, на карточках её нет.

## Контекст

Форма создания в интерфейсе ([0149](0149-web-interface-module.md), [0152](0152-web-interface-frontend-stack.md))
после первых рук показала три неудобства.

**Дело.** Чтобы поставить работу в существующее дело, форма требовала два поля — идентификатор
и время создания дела: REST принимает дело парой `executionId` и `executionCreatedAt`
([0140](0140-rest-controllers.md)), потому что время создания — ключ партиционирования. Человек
знает идентификатор из лога или ссылки; время создания ему взять неоткуда.

**Входящие.** Запустить руками процесс, который начинается с входящей коммуникации, из интерфейса
нельзя: [0011](0011-communication-model.md) и [0053](0053-inbound-reception-modes.md) решили, что
входящие создаёт потребитель, и «собственного приёмного endpoint стартер не даёт». Причина решения —
стартер не должен становиться входом для внешней системы: у него нет её аутентификации, формата
адреса, ответа отправителю.

**Приоритет.** Пустое поле приоритета значит «по умолчанию», но какое это число, форма не знает:
приоритет разрешается по лестнице настроек ([0060](0060-retry-and-lease-configuration.md),
[0084](0084-priority-only-per-type.md)) и свой у каждого типа задачи и внешней системы.

## Рассмотренные варианты

### Дело

- **Оставить пару полей.** Неудобно ровно настолько, насколько описано. Отвергнуто.
- **Только из экрана дела**, полей в форме нет. Нельзя поставить работу в дело, известное
  по идентификатору из лога. Отвергнуто.
- **Только идентификатор, время находит сервер.** Поиск дела без времени — обход партиций
  таблицы дел, как у `GET /executions/{id}` без `createdAt`; при создании это один запрос.
- **Идентификатор в форме и кнопка «Создать в этом деле» на экране дела и на карточках — выбрано.**
  Кнопка открывает форму с уже известной парой, и сервер ничего не ищет; поле принимает и один
  идентификатор.

### Входящие

- **Не делать, ручной запуск — постановкой задачи.** Процесс, который начинается входящей,
  так не запустить: его вход — процессор входящих. Отвергнуто.
- **Ручной приём в REST, включён вместе с REST.** Любой, кому открыт `POST` REST, сможет выдать
  себя за внешнюю систему в любом окружении. Отвергнуто.
- **Ручной приём в REST за отдельным выключателем, по умолчанию выключенным — выбрано.**
  `taskcomm.rest.manual-inbound`. Включают там, где ручной запуск нужен; где выключен, пути нет
  вовсе — контроллер не создаётся.

### Приоритет

- **Подсказка текстом «из настроек типа».** Не отвечает на вопрос «какое число». Отвергнуто.
- **Итоговые приоритеты в API чтения и в `/meta` — выбрано.** `TaskInspection.defaultPriorities()`
  и `CommunicationInspection.defaultPriorities()`: тип или система с процессором → итоговый
  приоритет по умолчанию. `rest` читает их через API, как и всё остальное
  ([0087](0087-architecture-rules.md)).

## Решение

- Создание задачи и исходящей коммуникации в REST принимает дело и одним `executionId`: время
  создания сервер находит через `ExecutionService.find`; не нашёл — `400`. Пара по-прежнему
  принимается и обходится без поиска. Чтение списков дело по-прежнему требует парой.
- `POST {base-path}/communications/inbound/{source}` — асинхронный приём входящей через
  `CommunicationService.receive`, тем же путём, что у приёма потребителя: тело как есть, `Content-Type`
  запроса — его заголовок, необязательные `requestId`, `dedupKey`, `correlationId`. Ответ — `201`
  с коммуникацией; у дубликата — с совпавшей, у неразбираемого тела — с причиной. Контроллер
  создаётся, только если `taskcomm.rest.manual-inbound: true`; по умолчанию `false`. Путь
  под `taskcomm.rest.base-path` и закрыт `taskcommRequestMatcher`.
- `/meta`: у типа задачи и у внешней системы — `defaultPriority`; у коммуникаций — признак
  `manualInbound`.
- Интерфейс: форма создания — в боковой панели поверх текущего экрана; ссылка «Создать»,
  открытая в новой вкладке, ведёт на страницу формы, как раньше. Кнопка «Создать в этом деле»
  на экране дела и на карточках. Вкладка входящей — только при `manualInbound`.

## Последствия

- **Изменены [0011](0011-communication-model.md) и [0053](0053-inbound-reception-modes.md):**
  приёмный путь у стартера теперь есть — ручной, выключенный по умолчанию. Внешним системам
  его не отдают: аутентификация у него — та же, что у человека в интерфейсе.
- В публичном API — два новых метода чтения. Интерфейсы реализует стартер ([0138](0138-inspection-api.md));
  своя реализация у потребителя перестанет компилироваться.
- Создание по одному идентификатору — лишний запрос с обходом партиций таблицы дел.
- Входящая, созданная руками, неотличима от пришедшей: в истории её видно только по экземпляру
  и времени. Отметки «создано из интерфейса» нет.

## Связанные решения

- [0140](0140-rest-controllers.md) — дело парой в REST; здесь при создании — и одним идентификатором.
