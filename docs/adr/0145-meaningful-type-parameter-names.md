# 0145. Осмысленные имена параметров типа

- **Дата:** 2026-11-07
- **Статус:** принято

## Контекст

[0059](0059-collect-contract.md) назвал параметры типа буквами: буква — уровень, `R` с тем же
суффиксом — результат уровня. Коммуникации получили `C`, `R`, `A`. Правило закреплено
в Checkstyle шаблоном `^R?[A-Z]$`.

На практике сигнатуры не читаются без расшифровки:

```
FlatTaskProcessor<T, RT>
UnitTaskProcessor<T, U, RU, RT>
BatchTaskProcessor<T, B, U, RU, RB, RT>

RestCommunicationProcessor<C, R, A>
```

Шесть букв подряд требуют держать в голове таблицу, а `R` у коммуникаций и `R` у задач значат
разное: синхронный ответ и префикс результата. 0059 сам признал, что без комментария к каждой
букве сигнатура не читается, — и комментарий стал обязательной частью каждого примера.

## Рассмотренные варианты

### A. Оставить буквы — отвергнуто

Конвенция Java, но расшифровка живёт в комментариях и в памяти читателя. В IDE потребителя
при реализации метода всплывают `RU`, `RB` — без Javadoc под рукой они ничего не говорят.

### B. Осмысленные имена с префиксом вида — выбрано

Первая буква — вид параметра, дальше по существу в CamelCase:

- `T` — тип;
- `E` — элемент коллекции или потока;
- `K` — ключ отображения;
- `V` — значение отображения.

Префикс отличает параметр типа от класса с тем же именем: `TRequest` не спутать с типом
`Request`. Нарушение конвенции Java сознательное: читаемость сигнатур публичного контракта
важнее привычки.

### C. Осмысленные имена без префикса — отвергнуто

`Payload`, `Result` сталкиваются с именами настоящих классов в коде потребителя и читаются
в сигнатуре как конкретный тип.

## Решение

Вариант B везде: публичный API, `internal` и тесты. Однобуквенные имена запрещены.

**Задачи.** У процессора — уровень и роль; у типов одного уровня — только роль:

```
FlatTaskProcessor<TTaskPayload, TTaskResult>
UnitTaskProcessor<TTaskPayload, TUnitPayload, TUnitResult, TTaskResult>
BatchTaskProcessor<TTaskPayload, TBatchPayload, TUnitPayload,
                   TUnitResult, TBatchResult, TTaskResult>

Task<TPayload>, TaskBatch<TPayload>, TaskUnit<TPayload>, Emitter<TPayload>
CollectedUnit<TPayload, TResult>, CollectedBatch<TPayload, TResult>
```

**Коммуникации.** Два вида ответа различаются способом доставки:

```
CommunicationProcessor<TRequest, TSyncResponse, TAsyncResponse>
Communication<TRequest>, SendResult<TRequest>
ReceiveAndProcessResult<TRequest, TSyncResponse>
```

**Остальное** называется по той же схеме: `Page<EItem>`, `BodyDecoder<TBody>`,
`TaskService.result(…, Class<TResult>)`.

Checkstyle проверяет шаблон `^[TEKV][A-Z][A-Za-z]*$` во всех четырёх модулях имён параметров
типа.

## Последствия

- **Совместимость не страдает.** Имя параметра типа не входит ни в исходный, ни в бинарный
  контракт: код потребителя, который подставляет конкретные типы, компилируется как прежде.
  Меняется только то, что потребитель видит в Javadoc и подсказках IDE.
- Полный набор параметров из [0059](0059-collect-contract.md) остаётся: меняются только имена.
- Сигнатуры стали длиннее; `BatchTaskProcessor` в объявлении потребителя по-прежнему удобнее
  писать по параметру на строку.
- Новый параметр типа называется по схеме сразу — Checkstyle не пропустит букву.
