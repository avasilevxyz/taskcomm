# Коммуникации

> Правила проекта, вынесенные из [CLAUDE.md](../../CLAUDE.md) по теме: транспортные контракты, приём, обмен, дедупликация, асинхронный ответ, размыкатель.
> Приоритет у них тот же, что у CLAUDE.md; обоснования — в [ADR](../adr/README.md).

## Транспортные контракты

Контракт процессора определяется **транспортом**, и иерархия запечатана дважды
([ADR 0052](../adr/0052-communication-transport-contracts.md)):

```java
sealed interface CommunicationProcessor<TRequest, TSyncResponse, TAsyncResponse>
        permits HttpCommunicationProcessor, KafkaCommunicationProcessor, RawCommunicationProcessor

sealed interface HttpCommunicationProcessor<TRequest, TSyncResponse, TAsyncResponse>
        extends CommunicationProcessor<TRequest, TSyncResponse, TAsyncResponse>
        permits RestCommunicationProcessor, SoapCommunicationProcessor
```

Третий параметр и метод `handleResponse` — для асинхронного ответа
([ADR 0086](../adr/0086-async-response-in-outbound.md)), см. «Асинхронный ответ» ниже. Имена
типов и методов API — [ADR 0134](../adr/0134-communication-public-api-shape.md).

- Воркер разбирает её pattern matching'ом **без ветки `default`** — то же правило, что у задач.
- Транспорт нужен стартеру до вызова процессора: разбор тела идёт **при создании** коммуникации,
  и кодек задаёт именно контракт.
- **Методы разбора `decodeRequest` и `decodeResponse` есть у каждого контракта**: по умолчанию JSON
  у REST и Kafka, XML у SOAP — разбор по умолчанию приходит аргументом, метод можно переопределить;
  у RAW оба обязательны. Исключение из метода разбора — неразбираемое тело
  ([ADR 0134](../adr/0134-communication-public-api-shape.md)).
- **SOAP по умолчанию снимает конверт**: корень — `Envelope` SOAP 1.1 или 1.2, разбирается первый элемент
  `Body`, DTD запрещены. `jackson-dataformat-xml` стартер **не тянет**: SOAP-процессор, полагающийся на разбор
  по умолчанию, без неё в classpath — падение при старте
  ([ADR 0135](../adr/0135-communication-engine.md)).
- Форма контракта — колонка `contract_shape` в `tc_communication`: `REST` | `SOAP` | `KAFKA` |
  `RAW`. У **входящих** проставляется **при создании** — в этот момент выбран кодек; у **исходящих** —
  при первом захвате
  ([ADR 0072](../adr/0072-contract-shape-check-on-children.md)). Несовпадение отменяет
  коммуникацию — как у задач.
- **Транспорт не входит в ключ реестра.** Процессор по-прежнему ищется по внешней стороне;
  транспорт — проверяемое свойство найденного, иначе к одной системе оказалось бы два процессора.
- Своего транспорта потребитель добавить не может: для экзотики есть `RawCommunicationProcessor`
  с сырым текстом.
- **Заголовки в контрактах процессоров — только свой нейтральный тип** поверх
  `Map<String, List<String>>`. Перегрузка с `HttpHeaders` допустима исключительно в методах приёма
  `CommunicationService`, под `@ConditionalOnClass`. `kafka-clients` в зависимостях не появляется
  никогда: тип в сигнатуре процессора необратим, потому что процессор не удаляется никогда.

## Приём входящих

Входящие коммуникации создаёт потребитель — из своего контроллера или слушателя, через API
стартера. Собственного приёмного endpoint стартер не даёт.

**Механика у всех коммуникаций одна** ([ADR 0074](../adr/0074-uniform-communication-processing.md)):
входящие и исходящие, без режимов приёма, могут иметь много попыток. Создание пишется
в транзакцию потребителя, обработку выполняет движок — захват, аренда, heartbeat, повторы,
переподхват по общим правилам. Режимов «синхронный / асинхронный» из
[ADR 0053](../adr/0053-inbound-reception-modes.md) больше нет, и колонки режима нет.

**Методов приёма два, выбор — в каждом вызове** ([ADR 0133](../adr/0133-synchronous-inbound-reception.md)):

- **Асинхронный** — создание в транзакции потребителя, обработку выполняет движок с повторами.
- **Синхронный** — коммуникация создаётся **своей короткой транзакцией, сразу с попыткой под арендой
  этого экземпляра**, чтобы её не взял поллер; процессор вызывается в потоке вызывающего, heartbeat
  продлевает аренду. Неуспех — попытка и коммуникация `FAILED` **без повтора**, вызывающий получает
  неуспех. **Внутри активной транзакции потребителя синхронный приём бросает исключение**, наследника
  `TaskcommException`, до записи чего-либо: попытка и обмен пишутся своими транзакциями и не увидели бы
  незакоммиченную строку, а работа рядом молча потеряла бы атомарность с бизнес-данными.
- **Ответ отправителю формирует процессор входящей** — его возвращаемое значение `TSyncResponse`. Стартер пишет его
  в `response_*` попытки в транзакции закрытия и отдаёт вызывающему. У асинхронного приёма `response_*`
  пуст — отвечать уже некому.
- **Повтор после смерти вызывающего** — по общим правилам: переподхват закрывает попытку `LEASE_LOST`,
  и стартер синхронную коммуникацию не отличает. Предел в одну попытку для системы, принимаемой
  синхронно, задаёт потребитель — аннотацией или в `yaml`; стартер это **не проверяет**, требование
  живёт в Javadoc и в [guide/communications/inbound.md](../guide/communications/inbound.md#входящие-синхронный-приём).

**Повторная доставка — своя коммуникация**, а не новая попытка на существующей
([ADR 0076](../adr/0076-communication-deduplication.md)). Совпал ключ дедупликации — она
становится `SKIPPED`, см. «Дедупликация» ниже. Упавшую коммуникацию восстанавливает ручной
перезапуск, а не повторная доставка.

Разбор тела — **при создании**, на уровне `CommunicationService`, в потоке контроллера: только так
вызывающий успевает ответить на неразбираемое тело ошибкой в правильном формате. В БД ложатся **обе
формы** — сырая текстом и доменная в `jsonb`; воркер берёт доменную и текст заново не разбирает.

**Неразбираемое тело — коммуникация создаётся сразу `FAILED`**, с попыткой, причиной и сырым телом.
Повторов нет: текст не станет валидным сам собой. Итог метода приёма сообщает о неразбираемом теле,
ошибку отправителю отвечает вызывающий; `response_*` пуст, callback-а для ответа нет
([ADR 0134](../adr/0134-communication-public-api-shape.md)).

Приём принимает **неизменяемое значение-запрос**, а запускает метод сервиса. Самозапускающегося
билдера нет сознательно: забытый терминальный вызов молча терял бы коммуникацию, а Java не умеет
`must_use`. Значение-запрос — `InboundRequest`, одно на оба метода приёма: `receive`
(асинхронный) и `receiveAndProcess` (синхронный). Итоги обоих — запечатанные типы: дубликат
и неразбираемое тело — их варианты, а не исключения ([ADR 0134](../adr/0134-communication-public-api-shape.md)).

## Системы без процессора

Правила из [ADR 0105](../adr/0105-orphan-communications.md) — по образцу задач типов без
процессора ([tasks.md](tasks.md), «Форма контракта»).

- **Создание коммуникации для системы без процессора отвергается исключением**, наследником
  `TaskcommException`, до записи чего-либо, — у входящих и у исходящих; через REST — ошибка
  клиента. Так же отвергается **приём колбэка** для такой системы: разбирать тело нечем.
- **Уже созданные коммуникации систем без процессора не захватываются и состояния не меняют.**
  Захват исключает неизвестные системы условием `= ANY(:известные)`; подстраховочные поллеры их
  не трогают — истёкшее ожидание ответа не открывает повторной отправки. Вернули процессор —
  поехали дальше сами.
- **Видимость — тремя каналами**: громкое предупреждение при старте с перечнем систем и числом
  коммуникаций, метрика осиротевших по системе ([observability.md](observability.md)), признак
  в REST-выдаче ([rest-and-search.md](rest-and-search.md)).

## Асинхронный ответ

Правила из [ADR 0086](../adr/0086-async-response-in-outbound.md). **Ответ от той же системы,
куда ушёл запрос, дописывается в исходящую коммуникацию**, а не создаёт новую. В закрытую попытку
по-прежнему не пишется ничего: пока ответа ждут, коммуникация не терминальна.

- **Отправка успешна, ответ ожидается** — статус `AWAITING_RESPONSE`, фаза `HANDLE_RESPONSE`,
  аренды нет. Пришёл колбэк — открывается попытка `HANDLE_RESPONSE`, движок захватывает её
  и вызывает **`handleResponse` процессора исходящей** под арендой, с heartbeat и повторами.
  Переход в эту фазу начинает новый цикл повторов (`retry_cycle_started_at = now()`).
- **Кто ждёт — определяет ключ корреляции** ([ADR 0104](../adr/0104-wait-defined-by-correlation-key.md)),
  у всех транспортов одинаково. Исходящая ждёт ответа, если у неё зарегистрирован хотя бы один
  ключ **той же системы**, что её `destination`, — при создании или из `process`. Ключа нет —
  не ждёт, успешная отправка даёт `SUCCEEDED` без WARN. Ключ только под другой системой — тоже
  не ждёт: такой колбэк становится отдельной входящей. Метод контекста один — **«не ждать»**:
  ключ нужен, а ответа не будет. Решение — по итогу `process`; исключение перебивает ожидание.
  Ключ на входящей ожидания не включает. Метод — `doNotAwaitResponse()`. Javadoc метода регистрации ключа
  обязан сказать, что регистрация включает ожидание.
- **Колбэк ровно один** и приходит **тем же транспортом от той же системы** — тогда процессор
  один. Колбэк под другим именем системы (ключ зарегистрирован с явной системой,
  [ADR 0075](../adr/0075-correlation-key-scoped-by-system.md)) остаётся **отдельной входящей**
  в деле якоря с ребром `RESPONSE`. Механизмов ответа два, и это осознанно.
- **Срок ожидания** — `response-timeout`, лежит в `next_attempt_at`. Истёкшие находит подстраховочный поллер
  с тактом `taskcomm.communication.safety.interval`; попытки отправки считаются с начала цикла повторов,
  новый цикл начинает только приход колбэка ([ADR 0136](../adr/0136-communication-dedup-and-callbacks.md)). Истёк — коммуникация уходит
  в `PENDING` / `PROCESS` на **повторную отправку** с backoff в пределах `retry.max-attempts`;
  исчерпано — `FAILED` «ответ не получен». Поздний ответ на прежнюю отправку принимается как ответ.
  Повторная отправка даёт внешней системе второй запрос — её идемпотентность обязательна.
- **Приём колбэка — свой метод `CommunicationService`** `receiveResponse`: `source`,
  `correlationId`, сырое сообщение; лукап по `(source, correlationId)`, разбор в потоке
  контроллера, в транзакции потребителя.
  - Ожидающая или ещё отправляющая без ответа — колбэк дописывается в неё. **Ранний колбэк**
    (отправка `RUNNING` или ждёт повторной отправки) записывается сразу открытой попыткой
    `HANDLE_RESPONSE`; отправка закрылась успехом — сразу `PENDING`, минуя ожидание. Ждавшая
    повторной отправки закрывает свою незахваченную попытку `PROCESS` исходом `SKIPPED`.
  - **Ранний колбэк — доказательство доставки** ([ADR 0099](../adr/0099-early-callback-proves-delivery.md)).
    Отправка закрылась неуспехом — с повторами, без них или после `doNotRetry` — или
    `LEASE_LOST`: повторной отправки и `FAILED` нет, коммуникация уходит в `PENDING` /
    `HANDLE_RESPONSE` с новым циклом повторов, а попытка отправки сохраняет свой настоящий исход.
    Отправка закрылась пропуском (`skip` или дубликат) — коммуникация `SKIPPED`, попытка ответа
    закрывается `SKIPPED` «отправка пропущена, ответ не обработан». На коммуникации стоит
    `cancel_requested_at` — при любом исходе отправки `CANCELLED`, попытка ответа закрывается
    `SKIPPED` «отменено». Колбэк в закрытой попытке остаётся сохранённым.
  - Проверку открытой попытки ответа и перевод сущности каждый, кто закрывает попытку отправки, —
    воркер, переподхват истёкшей аренды, отмена — делает **под блокировкой строки коммуникации**:
    приём колбэка правит ту же строку.
  - **Тело колбэка не разобралось** — колбэк записывается попыткой `HANDLE_RESPONSE`, сразу закрытой `FAILED`,
    исходящая — `FAILED` «колбэк не разбирается» без повторов; ещё отправляющуюся доводит до этого закрытие
    отправки ([ADR 0136](../adr/0136-communication-dedup-and-callbacks.md)).
  - Нашлась, но **уже не ждёт** — терминальна, ответ принят, отменена — входящая **сразу `FAILED`**
    «ожидающий запрос по ключу не найден», **в деле найденной**, с ребром `RESPONSE`. Сюда же
    попадает повторный колбэк.
  - Не нашлось ничего — та же `FAILED`-входящая в новом деле, WARN.
- `handleResponse` по умолчанию ничего не делает: ответ сохранён, коммуникация `SUCCEEDED`.
  Идемпотентность — та же, что у `process`, и пишется в Javadoc.

## Отмена и перезапуск

Вход — `CommunicationService.cancel` и `restart` по коммуникации и по снимку из
`CommunicationInspection`; результаты — `CommunicationCancelResult` и `CommunicationRestartResult`
(`Accepted` | `Rejected`) с причиной ([ADR 0139](../adr/0139-restart-api.md)). Обе операции — одной
транзакцией под блокировкой строки коммуникации.

- **Отмена** ставит `cancel_requested_at`. Ждущая захвата или ответа (`PENDING`, `AWAITING_RESPONSE`) —
  `CANCELLED` сразу, её открытая попытка закрывается `SKIPPED` «отменено». Работающая доигрывает и пишет
  настоящий исход; отправка, после которой ждали бы ответа, — `CANCELLED`. Терминальная не отменяется.
- **Перезапуск** — только `FAILED` без отметки отмены ([ADR 0071](../adr/0071-no-restart-after-cancel.md)),
  **всегда с обработки**: фаза `PROCESS`, новый цикл повторов, новая открытая попытка, у входящей —
  с копией запроса последней попытки обработки. Исходящая отправляется заново, даже если упала только
  обработка ответа. Ключи дедупликации снова не завершены. Входящая с неразобранным телом
  не перезапускается.
- **Колбэки прежних циклов — история.** «Колбэк уже был» и «пришёл неразбираемый колбэк» смотрят только
  на попытки ответа текущего цикла: открытую или начатую после `retry_cycle_started_at`.

## Хранение обмена

Запрос и ответ целиком лежат **в строке попытки**, колонками прямо в `tc_communication_attempt`
([ADR 0055](../adr/0055-communication-exchange-storage.md)). Отдельной таблицы нет: связь 1:1
по построению, а партиционирование и дроп вместе с агрегатом достаются бесплатно.

`request_id`, `request_at`, `request_headers`, `request_body`, `response_id`, `response_at`,
`response_status`, `response_headers`, `response_body`, `response_payload`.

- **Смысл направление-зависимый**: у входящей запрос — то, что прислали нам, ответ — то, что
  ответили мы; у исходящей наоборот.
- **Тела — `text`, оба.** Внешняя система отвечает чем угодно: JSON, XML, HTML от балансировщика,
  пустое тело. `jsonb` уронил бы запись именно на том сообщении, ради которого разбор и затевают.
  **Двоичные форматы кладутся base64** — и это обязано быть в комментарии к колонке.
- `request_at` / `response_at` — **свои колонки**, а не `started_at` / `finished_at` попытки:
  между захватом и отправкой процессор строит запрос и ждёт ограничитель скорости.
- `response_status` осмыслен у REST и SOAP, у брокеров пуст. Пустая половина строки — нормальное
  состояние, а не потеря данных.
- **Повтор входящей копирует `request_*` в новую попытку** (запрос пришёл один раз и не меняется);
  у исходящей копирования нет — каждая попытка строит свой запрос. Повторная доставка — своя
  коммуникация со своей попыткой и своим запросом ([ADR 0076](../adr/0076-communication-deduplication.md)).
- **В попытке `HANDLE_RESPONSE` смысл — как у входящей**: `request_*` — колбэк, `response_*` — что
  мы ответили его отправителю; при повторе `request_*` копируется. Доменная форма колбэка —
  колонка попытки **`request_payload`**, заполненная только в этих попытках: у сущности
  одноимённая колонка занята исходным запросом, и комментарии обязаны их различать
  ([ADR 0086](../adr/0086-async-response-in-outbound.md)).
- Запись идёт **двумя каналами**: внутри процессора — методами `CommunicationContext`, вне —
  при создании коммуникации. Каждая запись **немедленно, своей короткой транзакцией**: копить
  до конца попытки нельзя, иначе падение после отправки сотрёт то, ради чего всё писалось.
  В свою попытку воркер вправе писать всегда, даже потеряв аренду.
- **Индекс по `request_id` есть** — под разбор инцидентов и поиск через REST. Лукап идёт в окне
  чтения истории ([rest-and-search.md](rest-and-search.md)), а в режиме «искать везде» обходит все
  партиции; это операция разбора, а не горячий путь, и **переиспользовать её в захвате или
  диспетчеризации нельзя**.
- **Очистки тел нет.** `taskcomm.results.discard` — только про результаты детей у задач; тела
  коммуникаций уходят с дропом партиции. Это осознанно, хотя тела и самое объёмное в схеме.

## Дедупликация

Правила из [ADR 0076](../adr/0076-communication-deduplication.md). Ключ извлекает или считает
потребитель — формат знает только он: заголовок, ключ сообщения Kafka, хеш нагрузки. Стартер
хранит ключи и решает, дубликат ли коммуникация.

- **Дубликат не отбрасывается, а создаётся и становится `SKIPPED`**, с причиной «дубликат
  коммуникации `<id>` по ключу `<ключ>`». Строка и обмен есть у каждой доставки — видно, сколько
  раз прислали.
- **Ключей два вида**, оба у входящих и исходящих: **по всей истории** — `dedupKey(key)`;
  **по последней успешной** — `dedupKey(subject, key)`, предмет и значение (товар и хеш цены).
  Пространство ключа — направление и внешняя система.
- **Задать ключ можно трижды**, каждый способ необязателен: (ключ из `beforeProcess` или `process`, оказавшийся
  дубликатом, действует как `skip`), при создании; методом процессора,
  который движок вызывает при захвате перед `process` (по умолчанию ключей нет); из `process`
  методом контекста. Все получившиеся ключи принадлежат коммуникации; свой ключ повторно
  не проверяется — ни повтором, ни ручным перезапуском. Методы: при создании — `withDedupKey`
  значения-запроса и `dedupKey` опций исходящей, перед `process` — `beforeProcess` процессора,
  из `process` — `dedupKey` контекста.
- **Дубликат — если совпал любой ключ.** По всей истории — с ключом **любой** коммуникации,
  включая упавшие и отменённые. По последней — с ключом последней **успешной** с тем же предметом
  или любой **незавершённой** с тем же предметом и ключом. Ключи дубликатов не хранятся,
  поэтому дубликат дубликата не порождает.
- **Где обнаружен, там и `SKIPPED`**: при создании — коммуникация создаётся сразу `SKIPPED`,
  с закрытой `SKIPPED` попыткой, и метод создания возвращает идентификатор совпавшей; перед
  `process` — `process` не вызывается; в `process` — метод контекста отвечает, дубликат ли,
  `shouldStop()` становится `true`, нормальный возврат даёт `SKIPPED`, **исключение перебивает
  пропуск**. Ключ из `process` не отменяет того, что процессор сделал до вызова, — Javadoc обязан
  сказать это прямо.
- **Таблица `tc_communication_dedup` партиционирована, как коммуникации**, и ключи уходят вместе
  с партицией. Глобальность держит не уникальный индекс, а поиск **по всем партициям** под
  `pg_advisory_xact_lock` по хешу ключа (у ключа по последней — по хешу предмета). Несколько
  ключей — блокировки по порядку хешей. Ключ при создании проверяется в транзакции потребителя
  и держит блокировку до её коммита; ключи из процессора — своей короткой транзакцией.
- **Ключ при создании — только в транзакции `READ COMMITTED`**
  ([ADR 0095](../adr/0095-dedup-requires-read-committed.md)). При более строгом уровне снимок
  берётся до ожидания блокировки, и поиск не видит ключ, закоммиченный за время ожидания, —
  дубликат прошёл бы молча. Поэтому создание с ключом читает `current_setting('transaction_isolation')`
  (фактический уровень в базе, а не объявленный в Spring) и при уровне выше `READ COMMITTED`
  бросает исключение, наследника `TaskcommException`, до записи чего-либо; сообщение называет
  обходные пути — метод перед `process` или создание вне своей транзакции. Создание без ключей
  уровень не проверяет.
- `finished_at` и `succeeded_at` в строке ключа ставятся в транзакции, делающей коммуникацию
  терминальной, и снимаются ручным перезапуском: без них «последняя успешная» требовала бы
  соединения с коммуникациями по всем партициям.
- Горизонт дедупликации — **глубина хранения**: удалили партицию — ключ снова свободен.
- Дедупликация **не отменяет** требования идемпотентности к процессору: она защищает от повторной
  доставки и повторного содержания, идемпотентность — от повторного выполнения по истёкшей аренде.

## Порядок и скорость

Порядок выполнения коммуникаций **не гарантируется**, всё идёт параллельно. Ключа упорядочивания
нет; если понадобится — это переделка захвата, а не добавление колонки.

Ограничение скорости встроено и настраивается для каждой системы — **вызовов отправки исходящей в секунду**
(`rate-limit-per-instance` в `systems.<имя>` или `rateLimitPerInstance` на классе процессора; дробное —
реже раза в секунду). Воркер ждёт разрешения перед `process` под арендой; входящие и обработка ответа
не ограничиваются ([ADR 0137](../adr/0137-rate-limit-and-circuit-breaker.md)). Лимит действует
**на экземпляр приложения**, и свойство называется `rate-limit-per-instance` — имя не должно врать,
потому что три инстанса с лимитом 10 дадут внешней системе 30. Распределённый лимит можно добавить
позже, не переименовывая существующее свойство.

## Исход попытки по ответу и размыкатель

Правила из [ADR 0065](../adr/0065-communication-circuit-breaker.md).

**У коммуникаций успех — не просто нормальный возврат.** Записанный ответ с отказным статусом делает
попытку `FAILED` со всеми последствиями, включая повтор, даже если процессор вернулся нормально.
`status_description` при этом пишет стартер из ответа («ответ 503»). Правило действует **всегда**,
включён размыкатель или нет. У задач успех по-прежнему — отсутствие исключения; расхождение
сознательное.

- Отказные статусы — `failure-statuses` в `systems.<имя>`, **вне** `circuit-breaker`. Применяются **только к ответу
  исходящей**: у входящей `response_*` — наш ответ отправителю ([ADR 0135](../adr/0135-communication-engine.md)). По умолчанию
  зависят от транспорта: `5xx` и `429` у REST и SOAP (`4xx` не всегда проблема системы), **пусто
  у RAW** — смысл статуса знает только автор процессора, — у Kafka статуса нет.
- REST- или SOAP-процессор исходящей вернулся нормально, не записав ответ, — `SUCCEEDED` и WARN.
- `failure-statuses` применяются к синхронному ответу в попытке `PROCESS`; к попытке
  `HANDLE_RESPONSE` — нет: там `response_*` — наш ответ отправителю колбэка
  ([ADR 0086](../adr/0086-async-response-in-outbound.md)).

**Размыкатель — только у исходящих**, ключ — `destination`, **выключен по умолчанию**: пороги
не проверены нагрузкой, а размыкатель с неверными порогами молча перестаёт отправлять в исправную
систему. У входящих его нет: процессор входящей в `source` не ходит, и его отказы говорят о нас,
а не о ней.

- **Что считается.** Отказ — исключение из списка (пустой список, по умолчанию, — все исключения;
  сужается аннотацией на процессоре или в `yaml`, `yaml` сильнее) и отказной статус. Успех —
  нормальный возврат без отказного статуса. **Не считаются вовсе** исключение после `doNotRetry`
  и превышение предела обработки. Исключение вне списка всё равно делает попытку `FAILED` —
  список сужает только размыкатель.
- **Размыкание** — по доле отказов за окно времени при минимальном числе вызовов.
- **Разомкнутая система не захватывается**: её набор передаётся в запрос захвата тем же условием,
  каким основной поллер исключает системы выделенных. Попытки не сгорают — строку никто
  не захватил. Выделенный поллер, у которого разомкнуты все системы, в БД не ходит вовсе.
- **Настройка системы** — `systems.<имя>.circuit-breaker` с `enabled` и `exceptions` (полные имена классов);
  `yaml` сильнее атрибута `circuitBreakerExceptions`. Пропуск, потеря аренды, входящие и обработка ответа
  не считаются ([ADR 0137](../adr/0137-rate-limit-and-circuit-breaker.md)).
- **Возврат.** Ожидание до пробы растёт по правилам backoff, с обязательным джиттером. Проба —
  **отдельный захват `LIMIT k`** по этой системе, а не снятие фильтра: строки системы самые старые,
  и первый захват забрал бы ими весь `batch-size`. Проба удалась, только если **все `k`** вызовов
  успешны. У пробы **свой срок**: не дождались всех исходов — снова размыкаем. Взять оказалось нечего —
  замыкаем; свободных воркеров нет — проба в следующем такте без удлинения ожидания.
- **Состояние — в памяти экземпляра.** Синхронизация между экземплярами желательна и будет
  отдельным решением; свойство всё равно называется `circuit-breaker`, без `-per-instance`, и при
  синхронизации его смысл изменится — это объявляется в заметках к версии.
- **REST — только чтение**: состояние ответившего экземпляра с его именем в выдаче. Ручное
  размыкание и замыкание — вместе с синхронизацией, и **разовые**: перевести сейчас, дальше
  автоматика.
- **Считаются только попытки `PROCESS`.** Истечение срока ожидания асинхронного ответа не отказ —
  так же, как превышение предела обработки ([ADR 0086](../adr/0086-async-response-in-outbound.md)).
- Индикатор здоровья размыкатель **не трогает**; `oldest_claimable_age` разомкнутой системы
  не исправляется — её сообщения действительно опаздывают.
- Поток процессора не прерывается никогда: «прервали по времени» значит «закрыли попытку».
  От зависания без тайм-аута размыкатель не защищает — тайм-аут на клиенте обязан ставить
  потребитель, см. [guide/communications/outbound.md](../guide/communications/outbound.md).
