# Обновление версии

- **Миграции только добавляют.** При поэкземплярном обновлении новая схема какое-то время
  работает со старым кодом, и это безопасно. Удаление колонки — не раньше следующего выпуска после
  того, как код перестал ею пользоваться.
- **Порядок**: сначала миграции, потом новый код. Старый код на новой схеме работает, новый
  на старой — не запустится.
- **Выпущенный файл схемы не меняется никогда** — иначе у всех, кто его применил, сломалась бы
  контрольная сумма Liquibase.
- Миграция, требующая ручного вмешательства, — только с мажорной версией.

## Изменения по версиям

### 2.2.0: структура нагрузки, шаблоны названий, SQL чтений

Схема не менялась, публичный API только расширился — правок в коде не требуется.

- `PayloadShape` и `TaskInspection.payloadShape`, `CommunicationInspection.requestShape` — структура
  JSON нагрузки для шаблона и проверки в форме создания
  ([ADR 0160](../../adr/0160-payload-shape.md)).
- Необязательные `taskTitle()`, `batchTitle()` и `unitTitle()` у процессоров задач — шаблоны
  названий для интерфейса ([ADR 0162](../../adr/0162-task-title-template.md)). Подстановка не из
  полей поиска своего уровня валит старт, но без шаблонов всё работает, как раньше.
- `SqlQuery` и `default`-методы `…Sql` у `TaskInspection` и `CommunicationInspection`, пути REST
  `…/sql` — запрос к базе, которым читаются строки, для разбора
  ([ADR 0165](../../adr/0165-read-sql.md)). Своя реализация интерфейса чтения не ломается:
  по умолчанию методы бросают `UnsupportedOperationException`.

### 2.1.1: перезапуск плоской задачи

Схема не менялась, публичный API только расширился. На 2.1.0 перезапущенная упавшая плоская задача
(`FlatTaskProcessor`) захватывалась на раскрытие и падала с «захвачена по другой форме контракта»,
пока не кончались повторы ([ADR 0158](../../adr/0158-flat-task-restart-phase.md)). Такие задачи
после обновления достаточно перезапустить ещё раз.

У процессоров задач и коммуникаций появились необязательные `title()` и `description()` — название
и описание для интерфейса ([ADR 0159](../../adr/0159-processor-title-and-description.md)); без них
всё показывается, как раньше, ключом.

### 2.1.0: REST переехал на `/tc/api`

Путь REST по умолчанию сменился с `/api/taskcomm` на **`/tc/api`**, мажорная версия при этом
не поднималась ([ADR 0151](../../adr/0151-default-paths-under-tc.md)). Если вы не задавали
`taskcomm.rest.base-path` сами, после обновления REST отвечает по новому пути, а по старому — `404`.

- Конфигурация безопасности через `taskcommRequestMatcher` работает без правок: сопоставитель
  переезжает вместе с путями.
- **Правила безопасности, написанные строкой `/api/taskcomm/**`, после обновления не защищают
  ничего**: REST попадает под ваше правило для всех остальных путей, и если оно мягче — например,
  `authenticated()` вместо роли, — права на отмену, перезапуск и чтение обмена расширяются молча.
  До обновления перейдите на `taskcommRequestMatcher` или верните прежний путь (ниже).
- Правила, написанные по строке пути, — скрипты, клиенты других сервисов, прокси, балансировщик, —
  придётся поправить. Либо верните прежний путь одной строкой:

```yaml
taskcomm:
  rest:
    base-path: /api/taskcomm
```
