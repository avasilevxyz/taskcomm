# Встраивание в приложение

Как стартер уживается с вашим контекстом Spring, что в нём можно заменить своим и как он ведёт
себя на нескольких экземплярах и при остановке.

## Что стартер не делает за вас

Стартер подключают к чужим приложениям, и он не имеет права менять их поведение:

- **не регистрирует бинов, которыми пользуется ваше приложение** — ни `JsonMapper`, ни `TaskScheduler`,
  ни `Executor`, ни `ThreadFactory`. Ваш маппер веб-слоя, ваши `@Scheduled` и `@Async` остаются
  такими, какими были. Свои маппер, планировщик и пулы стартер держит внутри;
- **не включает глобальные механизмы Spring** — `@EnableScheduling`, `@EnableAsync`,
  `@EnableTransactionManagement`;
- **не сканирует пакеты** и не объявляет `@ControllerAdvice`: его обработчики ошибок действуют
  только на его контроллеры;
- **не трогает Spring Security** — см. [REST API](rest-api.md#безопасность);
- **не заводит свой пул соединений** — работает через ваш `DataSource`.

Отдаёт стартер ровно два бина чужих типов, и оба — вам, а не себе: `taskcommRequestMatcher`
(при REST и Spring Security) и `taskcommHealthIndicator` (при Actuator).

Процессоры — обычные ваши бины. Стартер собирает все реализации контрактов из контекста; как вы
их объявите, `@Component` или `@Bean`, — неважно.

## База и транзакции

Стартеру нужны `DataSource` и `PlatformTransactionManager`. Выбираются они одинаково:

- **один бин в контексте или один `@Primary`** — берётся он, настраивать ничего не надо;
- **несколько, и ни одного `@Primary`** — пометьте нужный:

```java
@Bean
@TaskcommDataSource
DataSource jobsDataSource() { ... }

@Bean
@TaskcommTransactionManager
PlatformTransactionManager jobsTransactionManager(@TaskcommDataSource DataSource dataSource) {
    return new DataSourceTransactionManager(dataSource);
}
```

Не пометили при нескольких кандидатах — приложение не запустится и перечислит их. Менеджер
обязан управлять тем же `DataSource`: если видно, что это не так, приложение тоже не запустится.

Создание задач и коммуникаций **всегда идёт в транзакции**: в вашей, если она открыта, иначе
в своей короткой. Ставить задачу из транзакции на другой базе нельзя. Подробно, с тем, почему
нельзя переносить пометку на другую базу у работающего приложения, — в
[Совместимости](compatibility.md#транзакции-какую-базу-и-какой-менеджер-берёт-стартер).

## Точки замены

Заменить внутренние компоненты стартера можно только в четырёх местах — бином своего типа,
помеченным квалификатором стартера. Бин того же типа без квалификатора стартер не возьмёт.

| Квалификатор                   | Тип бина                 | Что заменяет                                              |
|--------------------------------|--------------------------|-----------------------------------------------------------|
| `@TaskcommPayloadMapper`       | `JsonMapper` (Jackson 3) | Сериализацию нагрузок, результатов и доменных форм обмена |
| `@TaskcommScheduler`           | `TaskScheduler`          | Планировщик тактов поллеров, heartbeat, партиций и метрик |
| `@TaskcommWorkerThreadFactory` | `ThreadFactory`          | Создание потоков во всех пулах воркеров                   |
| `@TaskcommWorkerTaskDecorator` | `TaskDecorator`          | Обёртку каждого запуска работы в воркере                  |

Двух бинов с одним квалификатором быть не может. Остальное — хранилище, движок, захват —
не заменяется: это внутренние типы, совместимость которых не гарантируется.

## Сериализация нагрузок

Нагрузки задач, результаты и доменные формы обмена сериализуются Jackson 3 в `jsonb`. По умолчанию —
собственным маппером стартера с настройками Jackson по умолчанию, независимо от маппера вашего
веб-слоя.

Свой маппер — например, с вашими модулями:

```java
@Bean
@TaskcommPayloadMapper
JsonMapper taskcommMapper() {
    return JsonMapper.builder()
            .addModule(new MoneyModule())
            .build();
}
```

**Маппер определяет формат уже записанных данных.** Сменить у работающей системы naming strategy,
формат дат или набор модулей — то же, что переименовать поле в классе нагрузки: старые записи
прочитаются иначе, и молча. Что менять в классах нагрузки можно, а что нельзя, — в
[Совместимости](compatibility.md).

## Потоки и пулы

- **Воркеры** — свой пул на каждый поллер, размером `workers`. Готовый `Executor` подставить
  нельзя: стартер захватывает ровно столько работы, сколько воркеров свободно, и должен это знать.
- **Планировщик** — один на стартер: такты поллеров, heartbeat, обслуживание партиций, снимок
  метрик. Заменяя его своим, дайте ему **не меньше двух потоков** и не нагружайте своими задачами:
  задержанный heartbeat — истёкшая аренда и двойное выполнение.
- **Контекст в потоках воркеров.** Ваш код в процессоре выполняется в потоке стартера, где нет
  контекста вызывающего: ни Security, ни вашего MDC, ни трассировки. Восстановить своё — через
  `TaskDecorator`:

```java
@Bean
@TaskcommWorkerTaskDecorator
TaskDecorator tracing(Tracer tracer) {
    return runnable -> () -> {
        Span span = tracer.nextSpan().name("taskcomm-work").start();
        try (Tracer.SpanInScope scope = tracer.withSpan(span)) {
            runnable.run();
        } finally {
            span.end();
        }
    };
}
```

Ключи MDC стартера (`tc.executionId`, `tc.taskId`…) ставятся внутри и снимаются сами — см.
[Эксплуатация](operations.md#логи-и-mdc).

**Виртуальные потоки** можно включить своей `ThreadFactory`, но узким местом при росте числа
воркеров станет пул соединений с базой, а не потоки.

## Несколько экземпляров

Экземпляры делят работу через базу и ничего не знают друг о друге — настраивать ничего не нужно.

| Что                               | Кто делает                                        |
|-----------------------------------|---------------------------------------------------|
| Захват и выполнение работы        | Все экземпляры, каждый свою долю (`SKIP LOCKED`)  |
| Heartbeat                         | Каждый — для своих попыток                        |
| Переподхват истёкшей аренды       | Любой, кто первым заметит                         |
| Обслуживание партиций             | Один за такт — взявший блокировку                 |
| Подсчёт метрик очереди            | Один за такт; публикуют все одно и то же значение |
| Ограничение скорости, размыкатель | Каждый сам по себе                                |

Отсюда две вещи для эксплуатации: метрики очереди складывайте по экземплярам `max()`, а не
`sum()`; лимит скорости внешней системы делите на число экземпляров.

## Остановка приложения

При остановке контекста движок:

1. перестаёт захватывать новую работу;
2. ждёт работающих воркеров до 25 секунд, продолжая продлевать их аренду;
3. не дождавшись, пишет WARN и выходит: прервать ваш код стартер не может.

Попытки воркеров, не вернувшихся вовремя, закроет переподхват, когда истечёт аренда, и работа
выполнится повторно — ещё одна причина держать процессоры идемпотентными. Если в
`spring.lifecycle.timeout-per-shutdown-phase` у вас меньше 25 секунд, Spring может остановить
стартер раньше, чем он дождётся воркеров.
