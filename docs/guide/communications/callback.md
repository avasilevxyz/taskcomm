# Асинхронный ответ (колбэк)

Типичная интеграция: вы отправили запрос, внешняя система ответила «принято, номер Y», а результат
пришлёт через час в ваш контроллер — с номером Y и больше ничего. Чтобы ответ нашёл свою
исходящую, зарегистрируйте **ключ корреляции**:

- при создании — `CommunicationSendOptions.correlationId(id)`, если номер сгенерировали вы;
- из процессора — `context.registerCorrelationId(id)`, если номер вернула внешняя система.

**Исходящая с ключом своей же системы ждёт ответа.** После успешной отправки она переходит
в `AWAITING_RESPONSE` и стоит там, не держа аренды. Нет ключа — ждать нечего, отправка сразу
даёт `SUCCEEDED`. Ключ нужен, а ответа не будет — вызовите `context.doNotAwaitResponse()`.

Когда ответ придёт, передайте его стартеру:

```java
@PostMapping("/callbacks/supplier")
@Transactional
public ResponseEntity<Void> onSupplierCallback(@RequestBody String body, @RequestParam String ref) {
    ReceiveResponseResult result = communicationService.receiveResponse("supplier", CallbackRequest.of(ref, body));
    return ResponseEntity.ok().build();
}
```

Стартер найдёт исходящую по `(system, ref)` и **допишет ответ в неё**: откроет попытку обработки
ответа, и движок вызовет `handleResponse` того же процессора — под арендой и с повторами.
Запрос, синхронное «принято» и колбэк лежат в одной коммуникации, каждый в своей попытке.
`handleResponse` по умолчанию ничего не делает: колбэк сохранён, коммуникация `SUCCEEDED`.

`ReceiveResponseResult` говорит, куда попал колбэк:

| Вариант       | Что случилось                                                                                                                                                                      |
|---------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `Attached`    | Дописан в ждущую исходящую — обычный случай                                                                                                                                        |
| `Separate`    | Ключ зарегистрирован под **другой** системой (отправили по REST, ответ пришёл из Kafka) — колбэк стал отдельной входящей в деле исходящей и обработается процессором своей системы |
| `Unmatched`   | Дописаться некуда: ключ не найден или исходящая уже не ждёт. Колбэк сохранён входящей, сразу `FAILED`, и не обрабатывается никем                                                   |
| `Unparseable` | Тело колбэка не разобралось                                                                                                                                                        |

Что ещё нужно знать:

- **Ответ не пришёл за `response-timeout`** — коммуникация отправится заново по общим правилам
  повторов; исчерпав их, станет `FAILED` «ответ не получен». Повторная отправка — второй запрос
  во внешнюю систему, её идемпотентность обязательна. Поздний ответ на первую отправку
  засчитывается.
- **Ключ «на всякий случай» без `doNotAwaitResponse()`** — исходящая будет ждать ответа, которого
  не будет, и по истечении `response-timeout` отправится заново, до `max-attempts` раз.
- **Колбэк может опередить конец отправки** — он запишется и дождётся её. Пришедший колбэк —
  доказательство доставки: даже если отправка потом упала — по тайм-ауту вашего клиента,
  по отказному статусу, даже после `doNotRetry`, — повторной отправки не будет, сразу пойдёт
  `handleResponse`. Не считайте упавший `process` знаком того, что внешняя система ничего
  не получила. Колбэк не обработается, только если отправка закончилась пропуском или
  коммуникацию отменили ([ADR 0099](../../adr/0099-early-callback-proves-delivery.md)).
- **`handleResponse` обязан быть идемпотентным**, как и `process`: он выполняется под арендой
  и может быть повторён.
- **Ключ уникален в пределах системы**: «12345» одного поставщика не найдёт исходящую другого.
  Новый ключ не снимает прежних — их у коммуникации может быть несколько.

Колбэк не найдёт свою исходящую даже при зарегистрированном ключе в трёх случаях:

- **партиция исходящей уже удалена очисткой** — колбэк заведёт новое дело, сразу `FAILED`, с WARN.
  История, которой больше нет, связать не с чем;
- **тот же ключ той же системы уже занят другой коммуникацией** — так бывает, если внешняя система
  переиспользует свои номера. При регистрации ключ к новой коммуникации не переедет, будет WARN;
- **ответ пришёл под другим именем системы**, чем ушёл запрос (отправили по REST, ответ пришёл
  из Kafka), а ключ вы зарегистрировали без этого имени — колбэк станет `Unmatched`, с WARN.
  Зарегистрируйте ключ с системой ответа — `correlationId(system, id)`, — и колбэк станет `Separate`.

Первый и второй случаи ожидаемы, третий — ошибка регистрации. Работу по колбэку, которому некуда
дописаться, придётся сделать вручную.
