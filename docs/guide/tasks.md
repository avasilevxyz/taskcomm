# Задачи

Справочник по задачам: как писать процессоры, ставить задачи и управлять ими. Сквозные примеры
от начала до конца — в [Рецептах](recipes.md); что нельзя менять, когда задачи уже лежат
в базе, — в [Совместимости](compatibility.md).

## Выбор контракта

Форму работы выбирает тип задачи — через контракт, который реализует процессор.

| Если работа…                                                                  | Контракт                                  | Пример                                                 |
|-------------------------------------------------------------------------------|-------------------------------------------|--------------------------------------------------------|
| неделима: одна операция от начала до конца                                    | `FlatTaskProcessor<T, RT>`                | сформировать отчёт, выгрузить файл                     |
| идёт над множеством объектов, каждый обрабатывается и повторяется сам по себе | `UnitTaskProcessor<T, U, RU, RT>`         | синхронизировать заказы за март                        |
| то же, но объектам нужны общие данные, которые дорого получать поштучно       | `BatchTaskProcessor<T, B, U, RU, RB, RT>` | обновить цены: прайс-лист на поставщика, цена на товар |

Буквы параметров типа читаются по уровню: `T` — задача, `B` — группа, `U` — подзадача, а `R`
с той же буквой — результат этого уровня. `Void` на месте результата значит «не хранить».

Все три контракта требуют `taskType()` — строку, по которой стартер находит процессор. Два
процессора с одним типом — приложение не запустится.

## Плоская задача

```java
@Component
public class ReportProcessor implements FlatTaskProcessor<ReportParams, ReportSummary> {

    @Override
    public String taskType() {
        return "monthly-report";
    }

    @Override
    public ReportSummary process(Task<ReportParams> task, ProcessingContext context) {
        // вся работа здесь; нормальный возврат — успех, исключение — неуспешная попытка
        return new ReportSummary(rows, bytes);
    }
}
```

Задача считается выполненной, когда `process` вернулся без исключения. Возвращённое значение
сохраняется как результат задачи; `null` не сохраняется.

## Задача с подзадачами

Задача проходит три фазы: **раскрытие** порождает подзадачи, каждая **обрабатывается** отдельно,
**сборка** сводит их результаты в результат задачи.

```java
@Component
@RequiredArgsConstructor
public class OrderSyncProcessor
        implements UnitTaskProcessor<SyncPeriod, OrderRef, OrderOutcome, SyncSummary> {
    //                             T           U         RU            RT

    private final OrderRepository orders;

    @Override
    public String taskType() {
        return "order-sync";
    }

    @Override
    public void expand(Task<SyncPeriod> task, Emitter<OrderRef> units, ProcessingContext context) {
        orders.streamIds(task.payload().from(), task.payload().to())
                .forEach(id -> units.emit(new OrderRef(id)));
    }

    @Override
    public OrderOutcome process(TaskUnit<OrderRef> unit, ProcessingContext context) {
        return sync(unit.payload());   // один заказ
    }

    @Override
    public SyncSummary collect(
            Task<SyncPeriod> task, Stream<CollectedUnit<OrderRef, OrderOutcome>> units, ProcessingContext context) {
        return units.reduce(SyncSummary.empty(), SyncSummary::plus, SyncSummary::plus);
    }
}
```

**Раскрытие.** Порождённое отдаётся в `Emitter`, а не возвращается списком: стартер копит
подзадачи в буфере и пишет пачками, каждую своей короткой транзакцией. Ни миллион объектов
в памяти, ни миллион строк в одной транзакции. Отсюда правила:

- `Emitter` действителен только внутри вызова `expand` и не потокобезопасен. Сохранили в поле
  и вызвали позже — `IllegalStateException`.
- Раскрытие не атомарно. Упало посередине — уже записанные подзадачи становятся `ABANDONED`,
  а повтор раскрытия перечисляет источник **с начала** и порождает свой набор. Ни удалять
  прежних, ни отсеивать повторы не нужно.
- Раскрытие может честно вернуть **ноль** подзадач — это успех, а не ошибка. Сборка всё равно
  запустится, с пустым потоком.

Подзадачи идут в работу, когда раскрытие закончилось успехом.

**Обработка.** `process` вызывается для каждой подзадачи. Упала — повторяется **только она**,
соседи и задача не трогаются.

**Сборка.** Когда все подзадачи закончились, задача возвращается в очередь и получает вызов
`collect`. Что в него приходит:

- **поток, а не список** — читается страницами по мере потребления. Обрабатывайте лениво:
  `toList()` на миллионе подзадач положит ваше приложение;
- **все терминальные подзадачи**, а не только успешные. Каждая — `CollectedUnit` с id,
  нагрузкой, результатом, статусом и его описанием. Так в сводке можно назвать конкретный
  упавший объект. У неуспешных и у вернувших `null` результат пуст.

Статус задачи после сборки ставит стартер по детям:

| Дети                                                | Задача      |
|-----------------------------------------------------|-------------|
| все успешны (пропущенные не мешают)                 | `SUCCEEDED` |
| часть упала или отменена                            | `WARNING`   |
| ни одного выполненного, есть упавшие или отменённые | `FAILED`    |
| все пропущены                                       | `SKIPPED`   |
| детей нет                                           | `SUCCEEDED` |

Упала сама сборка и исчерпала попытки — задача `FAILED`, даже если все подзадачи успешны.

## Задача с группами

Уровень группы нужен, когда обработке объекта требуются общие данные, которые дорого получать
поштучно: прайс-лист на тысячу позиций, справочник курсов, пакетный ответ внешнего API.

```java
@Component
@RequiredArgsConstructor
public class PriceUpdateProcessor implements BatchTaskProcessor<
        UpdateParams,     // T  — параметры задачи
        SupplierBatch,    // B  — параметры группы
        ItemPrice,        // U  — один товар
        ItemOutcome,      // RU — что вышло с товаром
        SupplierReport,   // RB — свод по поставщику
        UpdateReport> {   // RT — свод по задаче

    private final SupplierApi supplierApi;

    @Override
    public String taskType() {
        return "price-update";
    }

    @Override
    public void expand(Task<UpdateParams> task, Emitter<SupplierBatch> batches, ProcessingContext context) {
        task.payload().supplierIds().forEach(id -> batches.emit(new SupplierBatch(id)));
    }

    @Override
    public void expandBatch(TaskBatch<SupplierBatch> batch, Emitter<ItemPrice> units, ProcessingContext context) {
        // один поход во внешнюю систему на всю группу
        PriceList list = supplierApi.fetchPriceList(batch.payload().supplierId());
        list.items().forEach(item -> units.emit(new ItemPrice(item.sku(), item.price())));
    }

    @Override
    public ItemOutcome process(TaskUnit<ItemPrice> unit, ProcessingContext context) {
        return apply(unit.payload());   // данные уже внутри подзадачи
    }

    @Override
    public SupplierReport collectBatch(
            TaskBatch<SupplierBatch> batch, Stream<CollectedUnit<ItemPrice, ItemOutcome>> units,
            ProcessingContext context) {
        return SupplierReport.of(batch.payload().supplierId(), units);
    }

    @Override
    public UpdateReport collect(
            Task<UpdateParams> task, Stream<CollectedBatch<SupplierBatch, SupplierReport>> batches,
            ProcessingContext context) {
        return UpdateReport.of(batches);
    }
}
```

**Данные, полученные при раскрытии группы, кладутся в нагрузку каждой подзадачи.** Подзадача
самодостаточна: её повтор через месяц не требует ни группы, ни задачи. Поэтому `B` — параметры
группы («какой поставщик»), а не собранные данные («его прайс-лист»).

Если общие данные объёмны и дублировать их в каждой подзадаче дорого, храните их у себя, ключуя
по `unit.batchId()`. Своего хранилища общих данных у стартера нет.

Группа проходит те же фазы, что задача с подзадачами: `expandBatch` — раскрытие, `collectBatch` —
сборка. Подзадачи группы идут в работу, как только раскрыта их группа, не дожидаясь соседних.

## Постановка задачи

`TaskService.submit` — по классу процессора или по строке типа:

```java
Task<SyncPeriod> task = taskService.submit(OrderSyncProcessor.class, new SyncPeriod(from, to));
Task<SyncPeriod> same = taskService.submit("order-sync", new SyncPeriod(from, to));
```

По классу надёжнее: компилятор проверит тип нагрузки, а переименование типа не сломает вызов.
Постановка по типу, для которого нет процессора, бросает исключение — опечатка в имени не станет
тихо зависшей задачей. Процессор помечен `@Deprecated` — постановка тоже отвергается, см.
[Совместимость](compatibility.md).

Редкие сочетания — через `TaskSubmitOptions`:

```java
taskService.submit(OrderSyncProcessor.class, period, TaskSubmitOptions.defaults()
        .priority(10)                          // меньше — важнее
        .notBefore(Instant.parse("2026-12-01T03:00:00Z"))
        .inNewExecution());                    // не наследовать дело процессора
```

| Опция                | Что делает                                                  |
|----------------------|-------------------------------------------------------------|
| `inExecution(ref)`   | Положить задачу в указанное дело                            |
| `inNewExecution()`   | Завести новое дело, даже если ставите из процессора         |
| `priority(n)`        | Приоритет этой задачи вместо значения по умолчанию для типа |
| `notBefore(instant)` | Не начинать раньше указанного момента                       |

Перегрузка `submit(type, payload, executionRef)` — короткая форма для `inExecution`.

**Транзакция.** Постановка пишется в вашу текущую транзакцию: задача видна воркеру с момента
коммита и исчезает при откате. Вне транзакции — например, из процессора — стартер открывает свою
короткую. Ставить задачу из транзакции на **другой** базе нельзя — исключение, а не тихое
расхождение. Подробно — [Совместимость](compatibility.md), раздел про транзакции.

**Из JSON.** `submitJson(type, json, options)` — для кода без доменной формы нагрузки, например
админки. JSON разбирается в тип нагрузки процессора сразу, до записи; не разобрался —
`UnreadablePayloadException`.

**Найти поставленные.** `findInExecution(execution, type)` — задачи указанного типа в деле,
в порядке создания.

## Контекст обработки

`ProcessingContext` приходит в каждый метод процессора.

| Метод                | Что делает                                                                        |
|----------------------|-----------------------------------------------------------------------------------|
| `skip(reason)`       | Объявляет исход «делать нечего». Действует при нормальном возврате                |
| `doNotRetry(reason)` | Запрещает повтор. Действует только вместе с исключением                           |
| `shouldStop()`       | Сигнал прекращения: отменили, потеряна аренда или вы сами вызвали `skip`          |
| `executionRef()`     | Ссылка на текущее дело — для создания из другого потока                           |
| `attemptNumber()`    | Номер попытки этой фазы в текущем цикле повторов, с единицы                       |
| `isRetry()`          | Была ли раньше попытка этой фазы — за всю историю, включая до ручного перезапуска |

Все методы отвечают из памяти и в базу не ходят.

**Пропуск.** `skip(reason)` — единственный способ сказать «делать было нечего»: это не успех
и не ошибка, а статус `SKIPPED` с сохранённой причиной.

```java
@Override
public OrderOutcome process(TaskUnit<OrderRef> unit, ProcessingContext context) {
    if (alreadySynced(unit.payload())) {
        context.skip("заказ уже синхронизирован");
        return null;
    }
    ...
}
```

Пропустить можно на любом уровне — подзадачу, раскрытие, сборку. Исключение после `skip`
перебивает пропуск. Пропуск и результат независимы: вызвали `skip` и вернули значение —
оно сохранится. Пропуск в сборке делает родителя `SKIPPED` поверх свода детей: упавшие дети
его уже не превратят в `WARNING`.

**Сигнал прекращения.** Если обработка длинная, спрашивайте `shouldStop()` между шагами и выходите,
когда он поднят. Различать причины не нужно — реакция одна. Учтите, что нормальный возврат
из недоделанной работы запишется успехом; чтобы отмена действительно остановила работу, выходите
исключением.

## Повторы и ошибки

**Ошибка — это исключение** из метода процессора. Попытка закрывается неуспехом, сущность
возвращается в очередь с паузой, которая растёт экспоненциально и случайно сдвигается
(`jitter`), — иначе тысяча подзадач, упавших из-за недоступности внешней системы, проснулась бы
одновременно и положила её снова. Исчерпала попытки — `FAILED`.

- Повторяется ровно тот уровень, что упал. Упала подзадача — повторится она. Упало раскрытие или
  сборка — повторятся они, под теми же правилами.
- **Лимит попыток у каждой фазы свой**: успешное раскрытие не тратит попыток сборки.
- Неуспешной считается и попытка, у которой истекла аренда (`LEASE_LOST`).

**Неповторяемая ошибка.** Битая нагрузка не станет валидной от повтора. Вызовите
`doNotRetry(reason)` **до** броска исключения — и сущность станет `FAILED` сразу:

```java
if (unit.payload().sku() == null) {
    context.doNotRetry("нет обязательного поля sku");
    throw new IllegalArgumentException("нет обязательного поля sku");
}
```

Без исключения `doNotRetry` ничего не делает, а вызвать его после броска невозможно — порядок
важен, и проверить его за вас нечем.

Параметры повторов — `max-attempts`, `initial-delay`, `multiplier`, `max-delay`, `jitter` —
задаются глобально, на тип задачи, на фазу и аннотацией на процессоре; см. ниже и
[Настройки](configuration.md).

## Аренда и долгие обработки

Пока ваш код работает, экземпляр держит аренду, а отдельный поток продлевает её на каждом такте
heartbeat. Три параметра:

| Параметр                   | Смысл                                                                                   |
|----------------------------|-----------------------------------------------------------------------------------------|
| `lease.duration`           | На сколько выдаётся и продлевается аренда. Столько ждёт работа после падения экземпляра |
| `lease.heartbeat-interval` | Как часто продлевается. Должен быть заметно меньше `duration`                           |
| `lease.max-execution-time` | Предел одной попытки. После него аренду перестают продлевать                            |

Превышение предела — обычная неуспешная попытка: она тратит лимит и включает паузу перед
повтором. Ваш код при этом не прерывается — поток остаётся занятым, пока вы не вернёте
управление, а результат опоздавшей попытки не сохранится. Отсюда два правила:

- **ставьте предел с запасом** к реальной длительности фазы. У раскрытия на миллион объектов
  и у обработки одного объекта профили разные — задавайте предел на фазу или на метод;
- **держите тайм-ауты на своих клиентах** короче предела: зависший вызов держит воркера.

Рост `LEASE_LOST` по типу задачи значит одно из двух: аренда коротка или предел затянут.

## Приоритет и порядок

**Шкала приоритета — по возрастанию: меньше значит важнее.** Приоритет 1 важнее приоритета 100.
По умолчанию — 100. Задаётся на тип задачи (аннотацией `@TaskPriority` или в `yaml`) и на
отдельную задачу при постановке. Подзадачи и группы наследуют приоритет задачи; перезапуск его
не меняет.

Как приоритет превращается в порядок, выбирает поллер — свойство `poll.claim-order`:

- **`deadline`** (по умолчанию) — каждый шаг приоритета откладывает срок работы на
  `poll.deadline-step`. Важная работа получает фору, но ограниченную, а ожидание не ограничено —
  поэтому неважная работа не голодает никогда. Взамен приоритет не абсолютен: 1 обгонит 100
  только внутри окна в 99 шагов;
- **`priority`** — строгий порядок: важное всегда раньше. Неважное может ждать бесконечно;
- **`quota`** — строгий порядок, но доля захватов `poll.fifo-share` идёт по очереди готовности,
  мимо приоритета.

**Выделенный поллер** — отдельная очередь со своим пулом воркеров для указанных типов. Основной
поллер эти типы не берёт. Так изолируют шумного соседа: тяжёлый ночной тип не займёт всех
воркеров, нужных срочной работе.

```yaml
taskcomm:
  task:
    pollers:
      urgent: { types: [order-urgent], workers: 4, claim-order: priority }
```

## Отложенный запуск

```java
taskService.submit(ReminderProcessor.class, reminder,
        TaskSubmitOptions.defaults().notBefore(Instant.now().plus(Duration.ofDays(1))));
```

Задача стоит в `PENDING` и не берётся в работу, пока момент не наступил. Отменить её можно и до
срока. Что нужно знать:

- **это не планировщик** — однократная отсрочка без повторяемости. Расписания и cron остаются
  за вами;
- **точность — до такта поллера**, а момент сравнивается с **часами базы**, не приложения;
- **ручной перезапуск отсрочку отменяет** — задача поедет сразу;
- **отложенная надолго задача удерживает свою партицию**: очистка не удалит срез данных,
  в котором лежит незавершённая работа.

Подробнее о последних двух — в [Совместимости](compatibility.md).

## Результаты

Значение, которое вернули `process`, `collect` или `collectBatch`, сохраняется в базе как
результат попытки. Раскрытие результата не возвращает: его результат — дети.

```java
Optional<SyncSummary> summary = taskService.result(task, SyncSummary.class);
```

`result` отдаёт результат **последней** попытки, если та успешна. Пусто — результата нет,
последняя попытка неуспешна или процессор возвращает `Void`.

**Результаты детей удаляются после сборки** — они уже сведены в результат родителя, а хранить
миллион ненужных строк дорого. Когда именно — свойство `taskcomm.results.discard`:

| Значение               | Когда удаляются результаты детей            |
|------------------------|---------------------------------------------|
| `after` (по умолчанию) | Через `discard-after` после успешной сборки |
| `immediately`          | Сразу после сборки                          |
| `never`                | Никогда — только вручную                    |

Вручную — `taskService.discardChildResults()` или `discardChildResults(olderThan)`. Вызов только
отмечает родителей, строки удаляет движок в фоне.

Удаление закрывает одну дорогу: **перезапустить отдельную подзадачу собранной группы уже нельзя**,
только группу или задачу целиком — сборке нужны результаты всех подзадач.

## Отмена и перезапуск

Обе операции работают на любом уровне — задача, группа, подзадача — и возвращают результат
с причиной, а не бросают исключение:

```java
TaskCancelResult cancel = taskService.cancel(unit);
if (cancel instanceof TaskCancelResult.Rejected rejected) {
    log.warn("отмена отвергнута: {}", rejected.reason());
}
```

Есть перегрузки по `Task`, `TaskBatch`, `TaskUnit` и по снимку из [API чтения](inspection.md).

**Отмена** кооперативная и **не скрывает сделанную работу**:

- то, что не работает, становится `CANCELLED` сразу;
- то, что работает, доигрывает и пишет **настоящий** исход: успешно закончившаяся после отмены
  подзадача станет `SUCCEEDED` — её побочные эффекты существуют. Упавшая после отмены
  не повторяется и становится `CANCELLED`;
- потомки, которые ещё не начинали работать, становятся `SKIPPED`; те, у которых попытки были, —
  `CANCELLED`;
- сборка у отменённого родителя не запускается;
- соседей отмена не трогает: задача, у которой отменили группу, доработает и закончится `WARNING`.

Терминальная сущность не отменяется.

**Перезапуск** устроен по-разному на разных уровнях:

| Уровень   | Из каких статусов                           | Что происходит                                                                |
|-----------|---------------------------------------------|-------------------------------------------------------------------------------|
| Подзадача | `FAILED`                                    | Заново `process`, соседи не трогаются                                         |
| Группа    | `SUCCEEDED`, `WARNING`, `FAILED`, `SKIPPED` | Новое раскрытие: заново за общими данными, новый набор подзадач, затем сборка |
| Задача    | те же                                       | То же уровнем выше                                                            |

Перезапуск начинает новый цикл повторов — лимит попыток снова полный — и **возвращает предков
в работу**: задача выйдет из `WARNING`, дождётся перезапущенных и соберётся заново. Сборка
запустится один раз, когда закончится последняя перезапущенная подзадача.

Перезапуск отвергается, если:

- сущность или её предок **отменены** — отмена необратима, нужна работа — ставьте новую задачу;
- у предка **идёт сборка** — повторите, когда она закончится;
- подзадача принадлежит **не последнему раскрытию** — после перезапуска группы прежний набор
  подзадач стал историей; чинится перезапуском родителя;
- **результаты группы удалены** — перезапускайте группу или задачу.

Причина отказа называет мешающую сущность.

## Поля поиска

Отдельного бизнес-ключа у задач нет: найти работу по номеру заказа можно только поиском
по нагрузке, а искать можно только по полям, которые процессор объявил.

```java
@Override
public List<SearchableField> searchableUnitFields() {
    return List.of(
            SearchableField.string("order_id", "$.orderId", "Номер заказа", "Например, A-1024"),
            SearchableField.string("customer_inn", "$.customer.inn", "ИНН клиента"),
            SearchableField.number("amount", "$.amount"));
}
```

Объявления раздельные по уровням: `searchableTaskFields()`, `searchableBatchFields()`,
`searchableUnitFields()` — нагрузки уровней разных типов. Путь — `$` и имена через точку,
без массивов.

Объявления хранятся в базе и переживают выкатку: нагрузка годовой давности лежит в форме годовой
давности, и описание для неё нужно прежнее. Отсюда поведение при изменениях:

- **подпись и описание** правятся на месте при следующем старте;
- **смена пути или типа значения** — новое объявление рядом со старым; старое продолжает находить
  старые нагрузки, а поиск по имени ищет по обоим;
- **убранное из кода поле** остаётся в реестре и продолжает искаться. Удаление включается
  свойством `taskcomm.search.remove-undeclared-fields`.

Индексы под поиск стартер в рабочей базе сам не создаёт — при старте он проверяет их и пишет
предупреждение с готовым `CREATE INDEX`. Как искать — [API чтения](inspection.md)
и [REST API](rest-api.md).

## Настройки процессора аннотациями

Автор процессора лучше всех знает профиль своей работы и задаёт умолчания аннотацией;
эксплуатация переопределяет их в `application.yml`.

```java
@TaskPriority(50)
@TaskRetry(maxAttempts = 5)
@Component
public class OrderSyncProcessor implements UnitTaskProcessor<...> {

    @Override
    @TaskLease(maxExecutionTime = "2h")      // раскрытие на миллион заказов идёт долго
    public void expand(...) { ... }

    @Override
    @TaskLease(maxExecutionTime = "1m")
    public OrderOutcome process(...) { ... }
}
```

| Аннотация                | Что задаёт                                                        | Где                   |
|--------------------------|-------------------------------------------------------------------|-----------------------|
| `@TaskPriority`          | Приоритет по умолчанию для типа                                   | только на классе      |
| `@TaskLease`             | `duration`, `heartbeatInterval`, `maxExecutionTime`               | на классе и на методе |
| `@TaskRetry`             | `maxAttempts`, `initialDelay`, `multiplier`, `maxDelay`, `jitter` | на классе и на методе |
| `@TaskProcessorSettings` | Всё сразу                                                         | на классе и на методе |

Длительности — строками в формате Spring Boot: `"30s"`, `"2h"`. Аннотация на методе действует
только на свой метод и перекрывает аннотацию класса. **Любое значение из `yaml` сильнее любой
аннотации** — так эксплуатация во время инцидента может быть уверена, что её настройка
применилась. Полный порядок — в [Настройках](configuration.md#как-складываются-настройки).
