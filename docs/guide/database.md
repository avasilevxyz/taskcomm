# База данных

Всё, что касается PostgreSQL: какие таблицы стартер заводит, как применить и обновить схему,
как устроены партиции и очистка.

## Таблицы

Тринадцать таблиц с префиксом `tc_`, в вашей схеме по умолчанию. Каждая колонка снабжена
комментарием на русском — `\d+ tc_task` в `psql` объясняет схему сам.

| Таблица                                    | Что хранит                                                            | Партиции |
|--------------------------------------------|-----------------------------------------------------------------------|:--------:|
| `tc_execution`                             | Дела                                                                  | ✓        |
| `tc_task`, `tc_task_batch`, `tc_task_unit` | Задачи, группы, подзадачи                                             | ✓        |
| `tc_task_attempt`                          | Попытки всех трёх уровней: аренда, время, исход                       | ✓        |
| `tc_task_result`                           | Результаты попыток                                                    | ✓        |
| `tc_communication`                         | Коммуникации                                                          | ✓        |
| `tc_communication_attempt`                 | Попытки коммуникаций вместе с обменом: запрос, ответ, заголовки, тела | ✓        |
| `tc_communication_dedup`                   | Ключи дедупликации                                                    | ✓        |
| `tc_communication_correlation`             | Реестр ключей корреляции                                              |          |
| `tc_searchable_field`                      | Объявленные поля поиска                                               |          |
| `tc_partition_horizon`                     | Граница партиций, где ещё может лежать незавершённая работа           |          |
| `tc_metrics_snapshot`                      | Снимок метрик очереди на всю схему                                    |          |

Устройство, которое стоит знать:

- **идентификаторы — UUIDv7**: упорядочены по времени и не раскрывают объём работы;
- **нагрузка — `jsonb`**, сериализация Jackson. Имя Java-класса в базе не хранится: тип
  восстанавливается из параметров типа процессора;
- **время — из часов базы.** Аренда, повторы и отметки считаются от `now()` PostgreSQL,
  синхронизировать часы экземпляров приложения не нужно;
- **внешних ключей между задачей, группами и подзадачами нет** — партиционирование их
  не допускает; целостность держит код.

**Одна схема — одно приложение.** Стартер считает свои процессоры полным описанием всех типов
задач в схеме. Два сервиса на одной схеме увидят задачи друг друга как осиротевшие. Разводите
их по разным схемам.

## Применение схемы

Схему применяете вы; стартер создаёт только партиции. Схема поставляется **одним файлом на версию**
в jar стартера — `db/changelog/taskcomm/taskcomm-<версия>.sql`. Это Liquibase formatted SQL:
разметка changeSet'ов записана комментариями, и для любого другого инструмента это обычный SQL.

**Liquibase** — одна строка в вашем master:

```xml
<include file="db/changelog/taskcomm/master.xml" relativeToChangelogFile="false"/>
```

`master.xml` подключает файлы версий по порядку; они применяются вашим Liquibase к вашей
`DATABASECHANGELOG`. Подходят Liquibase 4.x и 5.x.

**Flyway и другие** — скопируйте файл версии к себе под своим номером миграции. На каждую
следующую версию стартера, меняющую схему, — следующий файл.

**`taskcomm.schema.initialize: always`** — схема применится при старте приложения. Только для
тестов и локальной разработки: обновлять схему этот путь не умеет.

**Проверка при старте.** Стартер сверяет свои таблицы и колонки с ожидаемыми для своей версии.
Не совпало — приложение не запустится и скажет, каких миграций taskcomm не хватает, вместо
ошибки `column does not exist` на третий день работы.

## Партиции

Основные таблицы партиционированы по **времени создания дела**: всё, что относится к одному делу,
лежит в одной партиции, сколько бы времени ни прошло. Ответ, пришедший через год, ляжет
в партицию своего дела — старые партиции остаются записываемыми.

Партиции **ведёт стартер** — это единственный DDL, который он выполняет сам: без заранее созданной
партиции вставка упадёт, и система встанет.

- **Размер** — `taskcomm.schema.partitions.period`: `day`, `week` или `month`. Границы в UTC,
  неделя с понедельника. Имя — `<таблица>_p<ГГГГММДД нижней границы>`, например `tc_task_p20261101`.
  **Размер выбирается один раз**: сменить его на работающей базе — значит не запуститься.
- **Запас** — `create-ahead` периодов вперёд. Партиции текущего периода создаются при старте,
  до начала работы; запас пополняется на такте `interval`.
- **Один экземпляр за такт.** Партиции обслуживает тот, кто взял advisory-блокировку; остальные
  пропускают такт.

**Вести партиции самому** — `manage: false`. Стартер ничего не создаёт и не удаляет, а только
проверяет при старте и на каждом такте, что партиция на текущий момент есть и запас не меньше
`create-ahead`. Нет партиции на сейчас — приложение не запустится.

## Очистка

Очистка — `DROP` целой партиции, а не `DELETE` строк. **По умолчанию выключена**:

```yaml
taskcomm:
  schema:
    partitions:
      drop: { enabled: true, retention: 180d }
```

- Глубина хранения `retention` отсчитывается **от верхней границы** партиции.
- **Партиция с незавершённой работой не удаляется.** Задача, созданная в январе и всё ещё
  работающая в апреле, удержит январскую партицию. Проверка повторяется под блокировкой в той же
  транзакции, что удаление; не удалось взять блокировку быстро — удаление переносится на следующий
  такт.
- Вместе с делами уходит всё: попытки, результаты, тела обмена, ключи дедупликации. После
  удаления вычищаются и ключи корреляции этого диапазона — колбэк к удалённому делу заведёт новое
  дело и запишет WARN.
- Отдельной очистки тел обмена нет. Если сообщения крупные, выбирайте глубину хранения с этим
  в уме.

Удалить результаты детей раньше партиции — отдельный механизм, `taskcomm.results.discard`, см.
[Задачи](tasks.md#результаты).

## Отложенные задачи и очистка

Партицию удерживает **любая** незавершённая запись в ней. Чаще всего это:

- **задача, отложенная надолго** — `notBefore` через год не даст удалить годовой срез данных;
- **осиротевшая задача или коммуникация** — тип или система без процессора: такая работа
  стоит в `PENDING`, пока процессор не вернётся.

Они же держат **границу активных партиций** — самую раннюю партицию, где ещё может лежать
незавершённая работа. Захват читает только партиции не старше границы, поэтому одна забытая
задача годовой давности заставит его читать год партиций. Стартер предупредит, если граница
старше `drop.retention`, и назовёт сущность, которая её держит. Отмените её или верните процессор.

## Обновление версии

- **Миграции только добавляют.** При поэкземплярном обновлении новая схема какое-то время
  работает со старым кодом, и это безопасно. Удаление колонки — не раньше следующего выпуска после
  того, как код перестал ею пользоваться.
- **Порядок**: сначала миграции, потом новый код. Старый код на новой схеме работает, новый
  на старой — не запустится.
- **Выпущенный файл схемы не меняется никогда** — иначе у всех, кто его применил, сломалась бы
  контрольная сумма Liquibase.
- Миграция, требующая ручного вмешательства, — только с мажорной версией.

## Размер и нагрузка

- **Самое объёмное — тела обмена** в `tc_communication_attempt`: по строке на каждую попытку,
  с запросом и ответом целиком. Затем подзадачи и их попытки — по строке на каждую попытку,
  успешную или нет.
- **Результаты детей** удаляются после сборки по `taskcomm.results.discard` — так миллион
  ненужных строк не ждёт удаления партиции.
- **Соединения.** Процессор работает вне транзакции и соединение не держит. Пул нужен под захват,
  запись попыток, heartbeat — по запросу на такт на экземпляр — и ваш собственный код в процессорах.
  Узким местом при росте числа воркеров становится пул соединений, а не потоки.
- **Индексы под поиск по нагрузке** стартер в рабочей базе не создаёт — это блокировки на живой
  таблице. При старте он пишет WARN с готовым `CREATE INDEX` для каждого объявленного поля без
  индекса. Применяйте их своими миграциями.
