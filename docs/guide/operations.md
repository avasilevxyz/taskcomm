# Эксплуатация и наблюдаемость

Что смотреть в работающей системе: метрики, алерты, health, логи — и что делать в типовых
ситуациях.

## Метрики

Метрики появляются, если в приложении есть Micrometer и бин `MeterRegistry`. Все имена начинаются
с `tc.`; имена и метки — контракт для ваших дашбордов, стартер меняет их только по правилам
совместимости. Метрик **двух родов**, и складываются они по-разному.

**Метрики экземпляра** — что сделал сам экземпляр. Складывайте по экземплярам как обычно
(`sum()`).

| Метрика                                | Метки                                     | Что это                                            |
|----------------------------------------|-------------------------------------------|----------------------------------------------------|
| `tc.task.attempt.duration`             | `type`, `level`, `phase`, `outcome`       | Длительность попыток задач                         |
| `tc.task.attempts`                     | `type`, `outcome`, `retry`                | Число попыток; отсюда доля ошибок и повторов       |
| `tc.communication.attempt.duration`    | `system`, `direction`, `phase`, `outcome` | Длительность попыток коммуникаций                  |
| `tc.communication.attempts`            | `system`, `outcome`, `retry`              | Число попыток коммуникаций                         |
| `tc.communication.breaker.state`       | `system`                                  | Размыкатель: 0 — замкнут, 1 — проба, 2 — разомкнут |
| `tc.communication.breaker.transitions` | `system`, `to`                            | Переходы размыкателя                               |

`outcome` — `succeeded`, `failed`, `skipped`, `lease_lost`.

**Метрики на всю схему** — состояние очереди. Их считает один экземпляр за такт
`taskcomm.metrics.interval` и кладёт в снимок в базе, а публикуют **все экземпляры одно и то же
значение**. Агрегируйте их `max()`: `sum()` умножит значение на число экземпляров.

| Метрика                        | Метки                      | Что это                                                                   |
|--------------------------------|----------------------------|---------------------------------------------------------------------------|
| `tc.task.queue`                | `type`, `poller`           | Готово к работе прямо сейчас и ждёт свободного воркера                    |
| `tc.task.delayed`              | `type`, `poller`, `reason` | Ждёт времени: `scheduled` — отложено, `retry` — пауза перед повтором      |
| `tc.task.oldest.claimable.age` | `type`, `poller`           | Возраст самой старой готовой работы, секунды                              |
| `tc.task.overdue`              | `type`, `poller`           | Просрочка с учётом приоритета, секунды — у поллеров с порядком `deadline` |
| `tc.task.unfinished`           | `type`                     | Незавершённые                                                             |
| `tc.task.orphaned`             | `type`                     | Незавершённые типов без процессора                                        |
| `tc.communication.*`           | `system` вместо `type`     | То же для коммуникаций                                                    |
| `tc.metrics.snapshot.age`      | `subsystem`                | Возраст снимка, секунды                                                   |

**Очередь — это только готовое к работе.** Ждущие паузы перед повтором и отложенные в неё
не входят: они ждут времени, а не мощности, и добавление экземпляров им не поможет. Поэтому
`queue` растёт, когда не хватает воркеров, а `delayed{reason=retry}` — когда что-то падает.

Тип или система без работы публикует нули, а не пропадает. Разбивки по приоритету нет.

## Алерты

Начните с этих:

| Условие                                                | Что значит                                                                                |
|--------------------------------------------------------|-------------------------------------------------------------------------------------------|
| `max(tc.task.oldest.claimable.age)` выше вашего SLA    | Работа опаздывает. Количество отвечает на «сколько», возраст — на «опаздываем ли»         |
| `max(tc.task.overdue)` больше нуля долго               | Кто-то опаздывает сверх своей форы по приоритету — при порядке `deadline` точнее возраста |
| `max(tc.task.orphaned)` больше нуля                    | Есть работа типа без процессора; она стоит и не поедет сама                               |
| `max(tc.metrics.snapshot.age)` больше двух-трёх тактов | Снимок никто не обновляет — значения очереди застыли                                      |
| `tc.communication.breaker.state == 2`                  | Система разомкнута, её сообщения ждут                                                     |
| рост `tc.task.attempts{outcome="lease_lost"}`          | Аренда коротка или предел обработки затянут; возможны двойные выполнения                  |
| доля `outcome="failed"` в `tc.*.attempts`              | Ошибки обработки                                                                          |

Те же условия — для `tc.communication.*`. У разомкнутой системы законно растёт
`oldest.claimable.age`: её сообщения действительно опаздывают.

## Health indicator

При Actuator появляется компонент `taskcomm` в `/actuator/health`. Он отвечает на один вопрос:
**жив ли движок на этом экземпляре**. `DOWN` — поток поллера или heartbeat не тикал дольше
`taskcomm.health.missed-intervals` своих тактов.

В индикатор сознательно **не входят** длина очереди, истёкшие аренды и доступность базы
и внешних систем. Индикатор, краснеющий под нормальной нагрузкой, перезапускал бы здоровые
экземпляры и обесценил бы мониторинг всего приложения. Для очереди есть метрики, для базы —
свой индикатор Spring Boot.

Выключить — `management.health.taskcomm.enabled: false`.

## Логи и MDC

Пока выполняется ваш процессор, в MDC лежат ключи стартера с префиксом `tc.`:
`tc.executionId`, `tc.taskId`, `tc.batchId`, `tc.unitId` или `tc.communicationId`, `tc.attempt`.
Префикс меняется свойством `taskcomm.logging.mdc-prefix`.

**Свой бизнес-идентификатор кладите в MDC сами**, обычным `MDC.put(...)` в процессоре:

```java
@Override
public OrderOutcome process(TaskUnit<OrderRef> unit, ProcessingContext context) {
    MDC.put("orderId", unit.payload().id());
    ...
}
```

Снимать его не нужно: по выходе стартер восстанавливает MDC целиком, каким он был до вызова, —
утечки в пул потоков не будет. Лог неуспешной попытки пишется до восстановления, так что ваш
идентификатор в нём есть. В строках, которые стартер пишет **вне** вызова процессора, — захват,
истечение аренды, закрытие родителя, — вашего идентификатора нет: взять его там неоткуда.

**При старте** стартер пишет:

- итоговые настройки по каждому типу, системе и методу процессора — с уровнем, откуда взято
  значение;
- громкие предупреждения: ни одного процессора; типы и системы без процессора с числом их
  незавершённой работы; устаревшие (`@Deprecated`) типы; недостающие индексы под поиск с готовым
  DDL; сомнительные настройки.

## Осиротевшие задачи и коммуникации

**Осиротевшая** — незавершённая работа типа задачи или внешней системы, для которой в приложении
нет процессора. Так бывает, если процессор удалили, переименовали тип или систему, или выкатили
версию без процессора.

Такая работа **не берётся и не меняет состояния** — она стоит в `PENDING` и поедет сама, как только
процессор вернётся. Видна тремя способами: предупреждением при старте, метрикой
`tc.*.orphaned` и признаком `orphan` в REST и API чтения.

Что делать:

- **процессор пропал по ошибке** — верните его, работа доделается;
- **тип переименовали** — верните процессор под старым именем, помеченный `@Deprecated`,
  и дайте ему доработать: тип задачи — ключ данных, см. [Совместимость](compatibility.md);
- **работа не нужна** — отмените её.

Осиротевшая работа держит свою партицию от удаления — дольше ждать не значит безопаснее.

## Типовые действия

| Ситуация                                      | Что делать                                                                                             |
|-----------------------------------------------|--------------------------------------------------------------------------------------------------------|
| Часть подзадач упала, задача в `WARNING`      | Найдите упавшие (`status=FAILED`, `parentId`) и перезапустите — только их; задача соберётся заново     |
| Упали из-за общих данных группы               | Перезапустите группу: она заново сходит за данными и породит новые подзадачи                           |
| Работа больше не нужна                        | Отмените задачу. Работающие доиграют, ждущие не начнутся                                               |
| Внешняя система лежала, коммуникации `FAILED` | Перезапустите их; размыкатель на будущее избавит от сгоревших попыток                                  |
| «Мы вам это присылали?»                       | Найдите коммуникацию по `requestId` и откройте её попытки — там обмен целиком                          |
| «Что случилось с заказом A-1024?»             | Поиск по полю нагрузки без типа задачи найдёт все операции над ним; `tc.unitId` из выдачи ведёт в логи |
| Убедиться, что старый тип доработал           | Сводка по типам или `tc.task.unfinished{type="..."}` — ждите нуля                                      |
| Разрослась `tc_task_result`                   | `POST /tasks/discard-child-results` или `taskService.discardChildResults()`                            |

Все действия есть в [REST API](rest-api.md) и в Java API — [Чтение из кода](inspection.md),
[Задачи](tasks.md#отмена-и-перезапуск), [Коммуникации](communications.md#отмена-и-перезапуск).
