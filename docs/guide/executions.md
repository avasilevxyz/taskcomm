# Дела и связи

Как работа складывается в дело, как управлять привязкой и как найти всё, что связано с одним
поводом.

## Зачем дело

Один повод — пришедшее сообщение, нажатая кнопка, ночной запуск — обычно расходится на задачу,
её подзадачи, исходящие сообщения и ответы на них. **Дело** (`Execution`) собирает их вместе.
Каждая задача, группа, подзадача и коммуникация принадлежит ровно одному делу.

Что это даёт:

- **экран дела** — одним REST-запросом всё, что происходило вокруг повода, в порядке создания,
  с тем, кто кого создал;
- **поиск связанного** — задачи и коммуникации своего дела без поиска по всей истории;
- **дешёвое чтение** — дело хранится в одной партиции по времени своего создания, и знающий его
  `ExecutionRef` читает только её.

Статуса у дела нет: оно не завершается и не отменяется, а живёт, пока жива его партиция.

## Новое дело или существующее

| Где создаёте                                          | Что получится                             |
|-------------------------------------------------------|-------------------------------------------|
| в своём коде, вне процессора                          | новое дело                                |
| внутри процессора, в его потоке                       | дело обрабатываемой сущности              |
| с `inExecution(ref)` или перегрузкой с `ExecutionRef` | указанное дело — откуда бы вы ни вызывали |
| с `inNewExecution()`                                  | новое дело, даже внутри процессора        |

Ссылка на дело — `ExecutionRef(id, createdAt)`. Взять её можно:

- у созданной сущности — `task.executionRef()`, `communication.executionRef()`;
- в процессоре — `context.executionRef()`;
- по идентификатору из лога (`tc.executionId`) — `executionService.find(id)` вернёт `Execution`,
  а у него `ref()`. Этот поиск обходит все партиции: он для разбора, а не для горячего пути.

`ExecutionRef` — обычное неизменяемое значение. Его можно хранить у себя и передавать в другие
потоки и сервисы: дело не завершается, а старые партиции остаются записываемыми. Ссылка на дело,
которое очистка уже удалила вместе с партицией, даст ошибку при создании — громкую, а не тихую
потерю связи.

```java
@Transactional
public void startOnboarding(Customer customer) {
    Task<Onboarding> task = taskService.submit(OnboardingProcessor.class, new Onboarding(customer.id()));
    customer.setExecution(task.executionRef());   // позже положим в это же дело всё остальное
}
```

## Где привязку легко потерять

**Текущее дело живёт в потоке, в котором вызван процессор.** Создали задачу или коммуникацию
из своего пула, `CompletableFuture` или `@Async` внутри `process` — она молча окажется в новом
деле, и связь с текущим не возникнет. Ошибки не будет.

```java
ExecutionRef execution = context.executionRef();
CompletableFuture.runAsync(() -> communicationService.send("supplier", request, execution));
```

Передавайте дело явно — и привязка не зависит от потока. Вместе с делом теряется и указатель
«кем создана». Подробно, с обратным случаем, — в [Совместимости](compatibility.md#привязка-к-делу-где-её-легко-потерять).

## Поиск связанного

**Состав дела из кода:**

```java
List<Task<?>> syncs = taskService.findInExecution(execution, "order-sync");
List<Task<SyncPeriod>> typed = taskService.findInExecution(execution, OrderSyncProcessor.class);
List<Communication<?>> sent = communicationService.findInExecution(execution, "supplier");
```

Чтение идёт в одной партиции дела. Из `process` подзадачи его не вызывайте: миллион подзадач —
миллион запросов. В `collect` это один вызов.

**Кто кого создал.** У задачи и коммуникации есть `origin()` — указатель на создателя:

| `Origin`     | Значение                                                                                       |
|--------------|------------------------------------------------------------------------------------------------|
| `type`, `id` | Кто создал: задача, группа, подзадача или коммуникация, и её идентификатор                     |
| `attemptId`  | Попытка создателя, в ходе которой это случилось. У колбэка, ставшего отдельной входящей, пусто |
| `relation`   | `SPAWNED` — создано из процессора; `RESPONSE` — колбэк, ответ на исходящую                     |

Пустой `origin()` — норма: так выглядит корень дела, созданный из вашего кода. У групп
и подзадач указателя нет — их место в иерархии известно по родителю.

Через указатель процессор может дотянуться до данных породившей его коммуникации — номера запроса,
тела ответа, — прочитав её через [API чтения](inspection.md).

**Всё дело целиком** — одним запросом REST, см. [REST API](rest-api.md#дела): задачи, группы,
подзадачи, коммуникации и ключи корреляции, с указателями.
