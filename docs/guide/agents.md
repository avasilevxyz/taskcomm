# Для ИИ-агентов

Памятка для агента, который пишет код приложения-потребителя taskcomm. Она же лежит в
`taskcomm-autoconfigure.jar` как `META-INF/taskcomm/AGENTS.md`, со ссылками на руководство
той версии, из которой собран jar. Ищите её там: она совпадает с подключённой версией, а ветка
`main` на GitHub может уйти вперёд.

## Если вы подключили taskcomm

Запишите в инструкции проекта (`AGENTS.md`, `CLAUDE.md` или что читает ваш агент) одну строку:
что подключён taskcomm, какой версии и что памятка лежит в jar. Следующая сессия о taskcomm
иначе не узнает и будет восстанавливать API из байт-кода.

## Где что читать

Публичный API — всё вне пакетов `internal`. У каждого публичного типа есть Javadoc, его
исходники — в `taskcomm-autoconfigure-<версия>-sources.jar` в Maven Central. Пути вида
`docs/...` в Javadoc считаются от корня репозитория https://github.com/avasilevxyz/taskcomm
на теге этой версии.

## Как проверить статус

Работа идёт в фоне: вызов `submit` или `send` возвращает управление, когда задача
или коммуникация только записана. Чем кончилось, смотрите через API чтения — не через таблицы `tc_*`.

- **В тесте** — дождитесь итога через `TaskInspection` или `CommunicationInspection`, например
  Awaitility и `communicationInspection.find(id, HistoryWindow.everywhere())`; идентификатор
  отдаёт `send(...).communication().id()`. Ставить работу нужно вне откатываемой транзакции
  теста — [Дождаться выполнения](testing/README.md#дождаться-выполнения).
- **В запущенном приложении** — те же бины из своего кода или REST: `taskcomm.rest.enabled: true`
  и `GET {base-path}/communications/{id}/attempts` покажут каждую попытку с запросом, ответом
  и статусом — [REST API](api/rest.md). REST по умолчанию выключен не зря: он умеет отменять
  и перезапускать, поэтому включайте его только локально или закрыв пути —
  [Безопасность](api/rest.md#безопасность). Человеку то же видно в браузере, если подключён модуль
  `taskcomm-ui` — [Веб-интерфейс](api/ui.md); закрывается тем же `taskcommRequestMatcher`.
- **Что значат статусы** — [Понятия](start/concepts.md#статусы).

## Чего не видно из кода

Сигнатуры этого не скажут, а ошибка здесь стоит данных пользователя. Это выжимка: каждое
правило живёт на странице по ссылке, и при расхождении верна она.

- **Имя типа задачи, имя внешней системы и класс нагрузки — формат уже записанных данных.**
  `taskType()`, `externalSystem()`, поля класса нагрузки, транспорт процессора коммуникаций
  после первого выпуска не меняют молча: часть изменений теряет данные без единой ошибки.
  Название и описание для человека — `title()` и `description()`, их менять можно свободно.
  Создавая процессор, скажите пользователю об этом. Меняя — сначала
  [Совместимость](evolution/compatibility.md).
- **Задачи и коммуникации создавайте в транзакции приложения** — вместе с его данными.
  Откат отменит и их. Подробно — [Постановка](tasks/submitting.md), [Исходящие](communications/outbound.md).
- **Процессор обязан быть идемпотентным**: гарантия at-least-once, та же работа может прийти
  повторно — [Гарантии](start/concepts.md#гарантии).
- **Тайм-аут клиента внешней системы короче предела обработки попытки**, иначе попытку закроет
  стартер, а запрос продолжит висеть — [Исходящие](communications/outbound.md).
- **Поведение по умолчанию берите из руководства, а не из классов `internal`.** Умолчания
  и внутреннее устройство меняются между версиями без предупреждения; обещано только то,
  что в [Настройках](setup/configuration.md) и Javadoc публичного API.
- **Таблицы `tc_*` не читайте и не меняйте напрямую** — ни в коде, ни чтобы почистить данные
  после проверки. Для чтения — `TaskInspection`, `CommunicationInspection` и REST, для управления —
  отмена и перезапуск в `TaskService` и `CommunicationService`. Это правило живёт только здесь.
- **Интеграционные тесты — на PostgreSQL в Testcontainers**: встроенные базы не подходят —
  [Тестирование](testing/README.md).
