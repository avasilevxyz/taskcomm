# Коммуникации

Справочник по обмену с внешними системами: отправка, приём, асинхронные ответы, защита
от дублей и от перегрузки внешней системы. Сквозные примеры — в [Рецептах](recipes.md);
договорённости, которые стартер не может проверить за вас, — в [Совместимости](compatibility.md).

## Процессор и транспорт

Процессор коммуникаций — адаптер к **одной** внешней системе в обоих направлениях: входящие от неё
и исходящие к ней приходят в один `process`, а направление разбирается по типу коммуникации.

```java
@Override
public Ack process(Communication<Order> communication, CommunicationContext context) {
    return switch (communication) {
        case Communication.Outbound<Order> outbound -> send(outbound, context);
        case Communication.Inbound<Order> inbound -> accept(inbound, context);
    };
}
```

Параметры типа `CommunicationProcessor<TRequest, TSyncResponse, TAsyncResponse>`:

- `TRequest` — доменная форма запроса;
- `TSyncResponse` — доменная форма синхронного ответа: у исходящей — что ответила внешняя система, у входящей —
  что ответить отправителю. `Void` — не хранить;
- `TAsyncResponse` — доменная форма асинхронного ответа (колбэка) на исходящую. `Void` — ответа не ждём.

Контракт выбирается по **транспорту** — он определяет, как разбирается тело входящего сообщения:

| Контракт                      | Тело по умолчанию разбирается как                                          |
|-------------------------------|----------------------------------------------------------------------------|
| `RestCommunicationProcessor`  | JSON                                                                       |
| `SoapCommunicationProcessor`  | XML: снимается конверт SOAP 1.1 или 1.2, разбирается первый элемент `Body` |
| `KafkaCommunicationProcessor` | JSON                                                                       |
| `RawCommunicationProcessor`   | никак — `decodeRequest` и `decodeResponse` пишете вы                       |

Разбор переопределяется методами `decodeRequest(body, headers, decoder)` и
`decodeResponse(body, headers, decoder)`; разбор по умолчанию приходит в них аргументом —
им можно воспользоваться после своей подготовки тела. Исключение из метода разбора — тело
не разбирается.

**Что делает стартер, а что вы.** Стартер хранит коммуникацию и её обмен, раздаёт работу,
повторяет, ограничивает скорость, размыкает. Ходить во внешнюю систему, слушать её и отвечать
ей — ваш код: HTTP-клиент, слушатель Kafka, контроллер. Своего приёмного endpoint и своего
HTTP-клиента у стартера нет.

**SOAP по умолчанию требует `jackson-dataformat-xml`.** Стартер её не тянет. Нет её
в приложении, а SOAP-процессор полагается на разбор по умолчанию, — приложение не запустится
с подсказкой.

## Исходящие

```java
@Transactional
public void changePrice(String sku, BigDecimal price) {
    catalog.updatePrice(sku, price);
    SendResult<PriceUpdate> result = communicationService.send(SupplierProcessor.class, new PriceUpdate(sku, price));
}
```

Коммуникация пишется в вашу транзакцию и уходит после коммита. Дальше движок захватывает её
и вызывает `process`, в котором вы отправляете запрос.

`send` — по классу процессора или по имени системы: `send("supplier", payload)`. Системы без
процессора не существует для стартера — создание бросит исключение. Опции:

```java
communicationService.send(SupplierProcessor.class, update, CommunicationSendOptions.defaults()
        .priority(10)
        .notBefore(tomorrowMorning)
        .dedupKey(update.sku(), hash(update))      // не отправлять то же, что уже ушло
        .correlationId(requestNumber));            // ждать колбэка с этим номером
```

| Опция                                            | Что делает                               |
|--------------------------------------------------|------------------------------------------|
| `inExecution(ref)`, `inNewExecution()`           | Дело, как у задач                        |
| `priority(n)`                                    | Приоритет, меньше — важнее               |
| `notBefore(instant)`                             | Не отправлять раньше                     |
| `dedupKey(key)`, `dedupKey(subject, key)`        | Ключ дедупликации, см. ниже              |
| `correlationId(id)`, `correlationId(system, id)` | Ключ корреляции, см. «Асинхронный ответ» |

`SendResult` — запечатанный: `Created` или `Duplicate` с идентификатором совпавшей коммуникации,
если ключ дедупликации совпал прямо при создании.

**Отправка в процессоре.** Запишите запрос до отправки и ответ — как только получили, даже
отказной, и до того, как бросите исключение:

```java
private Ack send(Communication.Outbound<Order> outbound, CommunicationContext context) {
    String body = json.writeValueAsString(outbound.requestPayload());
    context.recordRequest(ExchangeMessage.of(body).withId(requestId));
    String answer = client.post().uri("/orders").body(body)
            .exchange((request, response) -> {
                String text = response.bodyTo(String.class);
                context.recordResponse(ExchangeMessage.of(text)
                        .withStatus(response.getStatusCode().value())
                        .withHeaders(CommunicationHeaders.of(response.getHeaders().asMultiValueMap())));
                return text;
            });
    return json.readValue(answer, Ack.class);
}
```

Каждая запись идёт в базу сразу, своей короткой транзакцией: упадёт экземпляр после отправки —
то, что ушло, всё равно останется в истории. Без записанного ответа стартер не узнает статус:
`503` пройдёт как успех. REST- или SOAP-процессор, вернувшийся без записанного ответа, даёт WARN.

## Входящие: асинхронный приём

Входящую коммуникацию создаёт ваш контроллер или слушатель. Асинхронный приём — `receive` —
создаёт её в вашей транзакции, а обрабатывает движок, с повторами, как исходящую. Контроллер
отвечает «принято» сразу.

```java
@PostMapping("/webhooks/shop")
@Transactional
public ResponseEntity<Void> onShopEvent(@RequestBody String body, @RequestHeader HttpHeaders headers) {
    InboundRequest request = InboundRequest.of(body)
            .withHeaders(CommunicationHeaders.of(headers.asMultiValueMap()))
            .withRequestId(headers.getFirst("X-Event-Id"))
            .withDedupKey(headers.getFirst("X-Event-Id"));
    return switch (communicationService.receive(ShopProcessor.class, request)) {
        case ReceiveResult.Accepted<ShopEvent> accepted -> ResponseEntity.accepted().build();
        case ReceiveResult.Duplicate<ShopEvent> duplicate -> ResponseEntity.ok().build();
        case ReceiveResult.Unparseable<ShopEvent> bad -> ResponseEntity.badRequest().build();
    };
}
```

- **Тело разбирается сразу, в потоке контроллера** — так ошибку разбора можно вернуть отправителю
  в его формате. Неразбираемое тело не теряется: коммуникация создаётся сразу `FAILED`, с сырым
  телом, без повторов, а `receive` вернёт `Unparseable`.
- **Повторная доставка** — новая коммуникация. С тем же ключом дедупликации она станет `SKIPPED`,
  а `receive` вернёт `Duplicate` с идентификатором первой.
- **`InboundRequest` — значение, а не билдер.** Построить его мало — передайте в `receive`.
  Забытый вызов оставит неиспользованное значение, которое подсветит IDE.

Процессор входящей вызывается движком, возможно не с первой попытки и не на этом экземпляре.
Идемпотентность обязательна так же, как у исходящей.

## Входящие: синхронный приём

Иногда отправителю нужен результат обработки в том же соединении. `receiveAndProcess` создаёт
коммуникацию и сразу обрабатывает её **в вашем потоке**, одной попыткой, а возвращённое
процессором значение `TSyncResponse` отдаёт вам для ответа.

```java
@PostMapping("/api/orders")
public ResponseEntity<?> placeOrder(@RequestBody String body) {
    return switch (communicationService.receiveAndProcess(OrderIntakeProcessor.class, InboundRequest.of(body))) {
        case ReceiveAndProcessResult.Processed<OrderRequest, OrderAnswer> ok -> ResponseEntity.ok(ok.response());
        case ReceiveAndProcessResult.Duplicate<OrderRequest, OrderAnswer> dup -> ResponseEntity.ok().build();
        case ReceiveAndProcessResult.Unparseable<OrderRequest, OrderAnswer> bad -> ResponseEntity.badRequest().build();
        case ReceiveAndProcessResult.Failed<OrderRequest, OrderAnswer> failed -> ResponseEntity.internalServerError().build();
    };
}
```

Три правила, которые стартер не проверит за вас:

- **задайте этой системе `max-attempts: 1`** — аннотацией или в `yaml`. Умрёт ваш поток —
  без этого предела коммуникация повторится в фоне, а её ответ уже некому будет отдать;
- **вызывайте вне своей транзакции.** Внутри неё синхронный приём бросает исключение:
  коммуникация коммитится до вызова процессора, и откат ваших данных её бы не откатил;
- **отвечайте тем, что вернул процессор, как есть** — стартер сохранил именно это значение как
  отданный ответ.

Неуспех процессора — коммуникация `FAILED` без повтора, вы получаете `Failed` с причиной.

## Асинхронный ответ (колбэк)

Типичная интеграция: вы отправили запрос, внешняя система ответила «принято, номер Y», а результат
пришлёт через час в ваш контроллер — с номером Y и больше ничего. Чтобы ответ нашёл свою
исходящую, зарегистрируйте **ключ корреляции**:

- при создании — `CommunicationSendOptions.correlationId(id)`, если номер сгенерировали вы;
- из процессора — `context.registerCorrelationId(id)`, если номер вернула внешняя система.

**Исходящая с ключом своей же системы ждёт ответа.** После успешной отправки она переходит
в `AWAITING_RESPONSE` и стоит там, не держа аренды. Нет ключа — ждать нечего, отправка сразу
даёт `SUCCEEDED`. Ключ нужен, а ответа не будет — вызовите `context.doNotAwaitResponse()`.

Когда ответ придёт, передайте его стартеру:

```java
@PostMapping("/callbacks/supplier")
@Transactional
public ResponseEntity<Void> onSupplierCallback(@RequestBody String body, @RequestParam String ref) {
    ReceiveResponseResult result = communicationService.receiveResponse("supplier", CallbackRequest.of(ref, body));
    return ResponseEntity.ok().build();
}
```

Стартер найдёт исходящую по `(system, ref)` и **допишет ответ в неё**: откроет попытку обработки
ответа, и движок вызовет `handleResponse` того же процессора — под арендой и с повторами.
Запрос, синхронное «принято» и колбэк лежат в одной коммуникации, каждый в своей попытке.
`handleResponse` по умолчанию ничего не делает: колбэк сохранён, коммуникация `SUCCEEDED`.

`ReceiveResponseResult` говорит, куда попал колбэк:

| Вариант       | Что случилось                                                                                                                                                                      |
|---------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `Attached`    | Дописан в ждущую исходящую — обычный случай                                                                                                                                        |
| `Separate`    | Ключ зарегистрирован под **другой** системой (отправили по REST, ответ пришёл из Kafka) — колбэк стал отдельной входящей в деле исходящей и обработается процессором своей системы |
| `Unmatched`   | Дописаться некуда: ключ не найден или исходящая уже не ждёт. Колбэк сохранён входящей, сразу `FAILED`, и не обрабатывается никем                                                   |
| `Unparseable` | Тело колбэка не разобралось                                                                                                                                                        |

Что ещё нужно знать:

- **Ответ не пришёл за `response-timeout`** — коммуникация отправится заново по общим правилам
  повторов; исчерпав их, станет `FAILED` «ответ не получен». Повторная отправка — второй запрос
  во внешнюю систему, её идемпотентность обязательна. Поздний ответ на первую отправку
  засчитывается.
- **Колбэк может опередить конец отправки** — он запишется и дождётся её. Пришедший колбэк —
  доказательство доставки: даже если отправка потом упала по тайм-ауту вашего клиента, повторной
  отправки не будет, сразу пойдёт `handleResponse`.
- **Ключ уникален в пределах системы**: «12345» одного поставщика не найдёт исходящую другого.
  Новый ключ не снимает прежних — их у коммуникации может быть несколько.

## Дедупликация

Дедупликация отсеивает повторную доставку входящего (та же запись Kafka после ребалансировки,
тот же запрос после тайм-аута у отправителя) и повторную отправку исходящего. Ключ считаете вы —
формат знаете только вы: заголовок, ключ сообщения, хеш нагрузки.

Видов ключа два:

| Ключ                                             | Дубликат, если…                                                                                                | Для чего                                                                                                 |
|--------------------------------------------------|----------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------|
| по всей истории — `dedupKey(key)`                | такой ключ есть у **любой** коммуникации этой системы и направления: в работе, успешной, упавшей, отменённой   | Идентификатор события: одно событие обрабатывается один раз                                              |
| по последней успешной — `dedupKey(subject, key)` | у **последней успешной** по этому предмету тот же ключ, или есть **незавершённая** с тем же предметом и ключом | Состояние предмета: не отправлять ту же цену того же товара второй раз, но отправить, если цена менялась |

Задать ключ можно трижды, все способы необязательны и складываются:

1. **при создании** — `InboundRequest.withDedupKey` или `CommunicationSendOptions.dedupKey`.
   Дубликат обнаруживается сразу, метод создания вернёт `Duplicate` с идентификатором совпавшей;
2. **в `beforeProcess` процессора** — движок вызывает его перед `process`. Дубликат — `process`
   не вызывается;
3. **из `process`** — `context.dedupKey(...)` ответит, дубликат ли это. Но то, что процессор
   успел сделать до вызова, уже сделано: если ключ можно посчитать заранее, считайте его раньше.

**Дубликат не исчезает, а становится `SKIPPED`** с причиной, называющей совпавшую коммуникацию.
Видно, сколько раз прислали.

Ограничения:

- ключ **при создании** работает только в транзакции `READ COMMITTED` — умолчание PostgreSQL
  и Spring. В более строгой изоляции создание с ключом бросит исключение;
- горизонт дедупликации — **глубина хранения**: ключи уходят вместе с партицией;
- дедупликация **не отменяет идемпотентности** — она защищает от повторной доставки, а не
  от повторного выполнения после истёкшей аренды;
- для **синхронного приёма** берите ключ по последней успешной: отправитель, получив ошибку,
  пришлёт снова, и ключ по всей истории совпал бы с упавшей.

## Корреляция

Ключ корреляции (`CorrelationKey`) и ключ дедупликации противоположны по смыслу: дедупликация
нужна, чтобы второй коммуникации **не появилось**, корреляция — чтобы ответ нашёл своё место.
Ключи живут в разных таблицах и друг с другом не пересекаются.

Корреляция — реестр «ключ системы → коммуникация». Поля `correlationId` на самой коммуникации
нет: истина только в реестре. Посмотреть ключи дела можно через
[API чтения](inspection.md) и выдачу дела в [REST](rest-api.md).

Ключ с явной системой — `correlationId(system, id)` — говорит: ответ придёт **от другой системы**.
Такой ключ ожидания не включает, а колбэк становится отдельной входящей **в том же деле**.

## Тела сообщений и заголовки

Обмен хранится **в каждой попытке**: идентификатор, время, заголовки и тело — отдельно запрос
и ответ, плюс доменная форма ответа. У входящей запрос — что прислали нам, ответ — что ответили
мы; у исходящей наоборот.

- **Тела хранятся как есть, текстом** — JSON, XML, HTML от балансировщика, пустое тело. Двоичные
  форматы кладите в base64.
- **У исходящей каждая попытка строит свой запрос**, и история показывает, что ушло на каждой.
  У входящей запрос пришёл один раз и копируется в новые попытки.
- **Отдельной очистки тел нет** — они живут, пока жива партиция. Крупные сообщения учитывайте,
  выбирая глубину хранения.

`ExchangeMessage` — запись обмена: тело и необязательные заголовки, идентификатор, время, статус.
`CommunicationHeaders` — нейтральные заголовки поверх `Map<String, List<String>>`, поиск имени
без учёта регистра. Типов `HttpHeaders` и Kafka в контрактах нет: иначе транспортная библиотека
приехала бы всем потребителям.

## Повторы и отказные ответы

У коммуникаций **нормальный возврат — ещё не успех.** Если процессор записал ответ с отказным
статусом, попытка становится `FAILED` и уходит в повтор, хотя исключения не было; причину
(«ответ 503») стартер пишет сам.

| Транспорт  | Отказные статусы по умолчанию        |
|------------|--------------------------------------|
| REST, SOAP | `5xx`, `429`                         |
| RAW        | нет — смысл статуса знаете только вы |
| Kafka      | статуса нет                          |

Список задаётся для системы — `failure-statuses` в `yaml` или `failureStatuses` в аннотации;
пустой список выключает правило. Применяется только к ответу **исходящей**: у входящей ответ —
наш собственный.

Остальное — как у задач: исключение — неуспешная попытка, пауза растёт экспоненциально
со случайным сдвигом, `context.doNotRetry(reason)` перед броском запрещает повтор. У фазы
отправки и фазы обработки ответа лимит попыток свой.

## Ограничение скорости

```yaml
taskcomm:
  communication:
    systems:
      supplier:
        rate-limit-per-instance: 10    # отправок в секунду; дробное — реже раза в секунду
```

Лимит считает вызовы отправки исходящих и действует **на экземпляр**: три экземпляра с лимитом 10
дадут внешней системе до 30. Воркер ждёт разрешения перед `process`. Входящие и обработка
колбэков не ограничиваются.

## Размыкатель

Размыкатель (circuit breaker) перестаёт отправлять в систему, которая отвечает отказами. Есть
только у **исходящих**, **выключен по умолчанию**:

```yaml
taskcomm:
  communication:
    systems:
      supplier:
        circuit-breaker: { enabled: true, exceptions: [java.io.IOException] }
```

- **Что считается отказом**: исключение из списка (пустой — любое) и отказной статус ответа.
  Не считаются исключение после `doNotRetry`, превышение предела обработки и истечение ожидания
  колбэка.
- **Когда размыкается**: доля отказов за окно `window` выше `failure-rate-threshold` при числе
  вызовов не меньше `minimum-calls`.
- **Что происходит**: коммуникации системы просто не захватываются — ждут в очереди, попытки
  не сгорают. Через растущий интервал `wait` стартер пробует отправить `probe.calls` коммуникаций;
  все успешны — размыкатель замыкается, иначе ждёт дольше.

Что нужно знать:

- **состояние у каждого экземпляра своё** — три экземпляра размыкаются каждый сам;
- **после замыкания накопленная очередь идёт волной**, её сдерживает только ограничение скорости;
- **от зависания без тайм-аута размыкатель не спасает**: превышение предела он не считает,
  а поток прервать нельзя. Тайм-аут на вашем клиенте — единственная защита.

Каждый переход пишет WARN с системой и долей отказов; состояние видно в метрике
`tc.communication.breaker.state` и в [REST](rest-api.md).

## Отмена и перезапуск

```java
CommunicationCancelResult cancel = communicationService.cancel(communication);
CommunicationRestartResult restart = communicationService.restart(communication);
```

Перегрузки — по коммуникации и по снимку из [API чтения](inspection.md); результат — `Accepted`
или `Rejected` с причиной.

- **Отмена**: ждущая отправки или ответа становится `CANCELLED` сразу; работающая доигрывает
  и пишет настоящий исход. Терминальная не отменяется.
- **Перезапуск** — только `FAILED` и не отменённой. Всегда с отправки или обработки: исходящая
  отправится заново, даже если упала только обработка ответа; входящая обработается заново
  с тем же запросом. Входящая с неразобранным телом не перезапускается.

Ручной перезапуск синхронно принятой входящей обработает её в фоне — ответ сохранится, но
отправителю его уже никто не отдаст.

## Настройки процессора аннотацией

```java
@CommunicationProcessorSettings(
        maxAttempts = 8,
        responseTimeout = "4h",
        rateLimitPerInstance = 10,
        failureStatuses = {"5xx", "429"},
        circuitBreakerExceptions = {IOException.class})
@Component
public class SupplierProcessor implements RestCommunicationProcessor<...> { ... }
```

Атрибуты те же, что у задач (приоритет, аренда, повторы), плюс `responseTimeout`,
`failureStatuses`, `rateLimitPerInstance` и `circuitBreakerExceptions`. Приоритет и отказные
статусы — свойства системы: на методе их задавать нельзя. Как у задач, **любое значение из `yaml`
сильнее аннотации** — см. [Настройки](configuration.md#как-складываются-настройки).
