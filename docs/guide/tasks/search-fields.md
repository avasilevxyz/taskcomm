# Поля поиска

Отдельного бизнес-ключа у задач нет: найти работу по номеру заказа можно только поиском
по нагрузке, а искать можно только по полям, которые процессор объявил. Поэтому идентификатор
бизнес-объекта **обязан лежать в нагрузке и быть объявлен**: не объявите номер заказа — найти
работу по нему будет нельзя ничем, кроме внутреннего идентификатора, а его никто не знает.

```java
@Override
public List<SearchableField> searchableUnitFields() {
    return List.of(
            SearchableField.string("order_id", "$.orderId", "Номер заказа", "Например, A-1024"),
            SearchableField.string("customer_inn", "$.customer.inn", "ИНН клиента"),
            SearchableField.number("amount", "$.amount"));
}
```

Объявления раздельные по уровням: `searchableTaskFields()`, `searchableBatchFields()`,
`searchableUnitFields()` — нагрузки уровней разных типов. Путь — `$` и имена через точку,
без массивов.

Объявления хранятся в базе и переживают выкатку: нагрузка годовой давности лежит в форме годовой
давности, и описание для неё нужно прежнее. Отсюда поведение при изменениях:

- **подпись и описание** правятся на месте при следующем старте;
- **смена пути или типа значения** — новое объявление рядом со старым; старое продолжает находить
  старые нагрузки, а поиск по имени ищет по обоим;
- **убранное из кода поле** остаётся в реестре и продолжает искаться. Удаление включается
  свойством `taskcomm.search.remove-undeclared-fields`.

Индексы под поиск стартер в рабочей базе сам не создаёт — при старте он проверяет их и пишет
предупреждение с готовым `CREATE INDEX`. Как искать — [API чтения](../api/java.md)
и [REST API](../api/rest.md).
